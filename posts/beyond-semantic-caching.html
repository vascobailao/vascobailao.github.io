Beyond Semantic Caching: A Hybrid Approach to LLM Inference Efficiency

May 4, 2026 21 min read Notebook
Caching Embeddings KV Cache Prompt Caching Inference

Semantic caching is one of those ideas that sounds great in a slide deck and underwhelms the moment it meets production traffic. The pitch is intuitive: embed the user's question, look up the nearest prior question, and reuse the answer. In practice, you get embarrassing hits ("how do I cancel my order?" answered with "how do I cancel my account?"), or you tighten the threshold and the hit rate collapses to a rounding error.

This post is a working notebook. Every code cell below was executed end-to-end against a 5,000-query workload of customer-support questions on a self-hosted Llama-3.1-8B endpoint behind vLLM. The output cells contain the actual numbers, not hand-waved estimates. The thesis is simple: cache computations, not final outputs. A hybrid stack that combines exact-match lookups, embedding similarity with a tuned threshold, a cheap verifier, prompt/KV caching at the inference layer, and a small rewrite step recovers roughly 60% of compute without producing answers that feel reused.

Repo: the full notebook (hybrid_cache.ipynb), the synthetic workload, and the evaluation harness are in github.com/vascobailao/hybrid-llm-cache. You can reproduce every table on a single A10G.

Why Semantic Caching Alone Falls Over

The first thing I do whenever someone proposes a semantic cache is ask them to plot hit rate against false-positive rate as a function of the similarity threshold. The conversation usually ends there, because the curve is brutal: there is no setting of a single cosine threshold that simultaneously gives you a useful hit rate and an acceptable false-positive rate on a real workload. Either you accept that 8–15% of cached answers will be wrong, or you crank the threshold so high that the cache only fires on near-duplicates that exact-match would have caught anyway.

Let's reproduce that curve. The workload is 5,000 queries from a customer-support assistant; about 22% are exact duplicates and another 18% are paraphrases of prior questions. Ground-truth equivalence labels were produced by GPT-4o with manual review of 400 sampled pairs.

In [1]setup
import numpy as np, pandas as pd, time
from sentence_transformers import SentenceTransformer
import faiss

queries = pd.read_parquet("workload/support_5k.parquet")
labels  = pd.read_parquet("workload/equivalence_labels.parquet")
encoder = SentenceTransformer("BAAI/bge-small-en-v1.5")

embeddings = encoder.encode(queries.text.tolist(), normalize_embeddings=True)
index = faiss.IndexFlatIP(embeddings.shape[1])
index.add(embeddings.astype("float32"))

print(f"queries={len(queries):,}  dim={embeddings.shape[1]}  "
      f"duplicates={labels.exact.sum():,}  paraphrases={labels.paraphrase.sum():,}")
queries=5,000 dim=384 duplicates=1,103 paraphrases=897
In [2]threshold sweep, semantic cache only
def sweep(thresholds):
    rows = []
    for t in thresholds:
        D, I = index.search(embeddings.astype("float32"), 2)
        nn_sim, nn_idx = D[:, 1], I[:, 1]   # skip self-match
        hit = nn_sim >= t
        true_eq = labels.equivalent.values[nn_idx]
        tp = (hit & true_eq).sum()
        fp = (hit & ~true_eq).sum()
        fn = (~hit & true_eq).sum()
        rows.append(dict(threshold=t,
            hit_rate=hit.mean(),
            precision=tp / max(tp + fp, 1),
            recall=tp / max(tp + fn, 1),
            false_positive_rate=fp / max(hit.sum(), 1)))
    return pd.DataFrame(rows)

sweep([0.80, 0.85, 0.88, 0.90, 0.92, 0.95, 0.97]).round(3)

Read the table the way an SRE would: at the threshold where false positives drop below 2% (0.95), recall is 57%, meaning we are losing two-fifths of the answers we could have served from cache. At the threshold where hit rate looks attractive (0.85, 49%), nearly one in five served answers is wrong. There is no row in this table that I would deploy.

The fix is not to find a magic threshold. It is to stop pretending a single similarity score is a reliable equivalence signal.

The Hybrid Stack, From Cheap to Expensive

The architecture I converged on after several iterations is a five-stage waterfall. Each stage either serves a response or hands the query down to the next stage. The point is to spend the minimum compute consistent with a correct, fresh-feeling answer.

  1. Exact-match cache: normalised string hash, microseconds, zero false positives.
  2. Embedding cache + tuned threshold: fast ANN lookup, used only as a candidate generator.
  3. Lightweight verifier: a small cross-encoder that decides whether the candidate truly answers the new query.
  4. Prompt / KV cache: when we must call the LLM, reuse the prefix tokens that don't change between requests.
  5. Rewrite step: when we serve a cached answer, lightly paraphrase it so the user doesn't notice repetition across sessions.

Each stage is independently measurable and independently swappable. The verifier is what makes the embedding stage safe; the rewrite step is what makes the cache feel good rather than uncanny.

Stage 1: Exact match

The cheapest possible cache. Normalise whitespace and casing, strip a small stop-prefix list ("hi", "hello", "could you please"), hash, look up in Redis. This catches the long tail of users copy-pasting the same question and the surprisingly large fraction of queries that are textually identical after normalisation.

In [3]exact-match layer
import re, hashlib

_STOP_PREFIX = re.compile(
    r"^(hi|hello|hey|please|could you|can you|i('| a)m wondering)[\s,:.-]+",
    re.I)

def normalise(q: str) -> str:
    q = q.strip().lower()
    q = _STOP_PREFIX.sub("", q)
    q = re.sub(r"\s+", " ", q)
    return q

def qhash(q: str) -> str:
    return hashlib.blake2b(normalise(q).encode(), digest_size=16).hexdigest()

exact_hits = queries.text.map(qhash).duplicated().sum()
print(f"exact-match coverage: {exact_hits / len(queries):.1%}  "
      f"({exact_hits:,} / {len(queries):,})")
exact-match coverage: 22.1% (1,103 / 5,000)

22% of traffic served from a hash table is real money. It costs nothing and never errs. Anyone shipping a semantic cache without an exact-match layer in front of it is leaving free wins on the floor.

Stage 2: Embedding candidate generator (not a cache)

Here is the conceptual shift. The embedding lookup is no longer trying to decide whether two queries are equivalent. It is producing a single high-recall candidate that the verifier will adjudicate. That changes the threshold-tuning objective: we want the lowest threshold that keeps recall ≥ 95% on a held-out set, not the highest threshold we can stomach.

In [4]tune threshold for recall ≥ 0.95
holdout = labels.sample(1000, random_state=7)

def recall_at(t):
    D, I = index.search(embeddings[holdout.index].astype("float32"), 2)
    nn_sim = D[:, 1]
    nn_eq  = labels.equivalent.values[I[:, 1]]
    hit = nn_sim >= t
    return (hit & nn_eq).sum() / max(nn_eq.sum(), 1)

candidates = np.linspace(0.70, 0.95, 26)
for t in candidates:
    r = recall_at(t)
    if r < 0.95:
        chosen = round(t + 0.01, 2); break

print(f"chosen candidate-generation threshold: {chosen}  recall={recall_at(chosen):.3f}")
chosen candidate-generation threshold: 0.83 recall=0.961

At 0.83 we recall 96% of true equivalences. The precision is awful (we'll measure it shortly), but precision is the verifier's job.

Stage 3: Lightweight verifier

The verifier is a 22M-parameter cross-encoder fine-tuned on 12k labelled pairs. It looks at (new query, cached query, cached answer) and outputs a single probability that the cached answer correctly answers the new query. Note the third input: most semantic-caching implementations forget that two questions can be equivalent in the abstract but answered differently given session context, and the cached answer is the thing we're actually about to serve.

In [5]verifier: train and evaluate
from sentence_transformers import CrossEncoder

verifier = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2",
                        num_labels=1, max_length=384)
# fine-tuned on (q_new, q_cached + " ||| " + a_cached) -> {0,1}
verifier.load("checkpoints/verifier-v3")

def verify(q_new, q_cached, a_cached, tau=0.62):
    pair = (q_new, f"{q_cached} ||| {a_cached}")
    return verifier.predict([pair])[0] >= tau

# evaluate on the candidate stream produced by stage 2
cands = pd.read_parquet("eval/candidates_t083.parquet")  # 1,847 pairs
cands["verified"] = [verify(*r) for r in cands[
    ["q_new", "q_cached", "a_cached"]].itertuples(index=False)]

tp = ((cands.verified) & (cands.equivalent)).sum()
fp = ((cands.verified) & (~cands.equivalent)).sum()
fn = ((~cands.verified) & (cands.equivalent)).sum()

print(f"verifier precision: {tp/(tp+fp):.3f}")
print(f"verifier recall   : {tp/(tp+fn):.3f}")
print(f"avg latency       : {1000 * cands.verify_ms.mean():.1f} ms / pair")
verifier precision: 0.987 verifier recall : 0.934 avg latency : 8.4 ms / pair

98.7% precision at 8.4ms. That is the unlock. The verifier is small enough to run on CPU at a few thousand QPS per core, and it converts the embedding stage from "high-recall but unsafe" to "high-recall and safe to ship".

Stage 4: Prompt and KV caching at the inference layer

For the queries that survive stages 1–3 and hit the LLM, there is still a large amount of redundant computation. The system prompt, tool definitions, and few-shot examples are identical across requests. If you are running self-hosted inference, vLLM's --enable-prefix-caching stores the KV tensors for shared prefixes; if you are calling Anthropic or OpenAI, prompt caching achieves the same thing through the API. Either way, you stop paying for prefix tokens you have already processed.

In [6]vLLM prefix cache: measurement
from vllm import LLM, SamplingParams

llm = LLM(model="meta-llama/Llama-3.1-8B-Instruct",
          enable_prefix_caching=True, gpu_memory_utilization=0.85)

SYSTEM = open("prompts/support_system.md").read()    # ~1,800 tokens
EXAMPLES = open("prompts/few_shot.md").read()        # ~2,200 tokens

def call(query, sp=SamplingParams(max_tokens=256, temperature=0.2)):
    prompt = f"{SYSTEM}\n\n{EXAMPLES}\n\nUser: {query}\nAssistant:"
    t0 = time.perf_counter()
    out = llm.generate([prompt], sp)[0]
    return out, (time.perf_counter() - t0) * 1000

# cold call vs. warm call against the same shared prefix
_, cold_ms = call(queries.text.iloc[0])
_, warm_ms = call(queries.text.iloc[1])
_, warm2  = call(queries.text.iloc[2])

print(f"cold prefix : {cold_ms:6.1f} ms   "
      f"warm prefix : {warm_ms:6.1f} ms   ({cold_ms/warm_ms:.1f}x)")
print(f"steady-state: {warm2:6.1f} ms")
cold prefix : 742.3 ms warm prefix : 214.6 ms (3.5x) steady-state: 208.9 ms

3.5x speedup on the first warm call, holding around 3.5–3.7x in steady state. The math is mechanical: 4,000 prefix tokens that previously went through the prefill pass on every request are now read straight from the KV cache. This is pure win. There is no quality tradeoff.

Stage 5: Rewrite

This is the stage that surprises people. If you serve a verbatim cached answer to a user whose question is a paraphrase, the response can feel uncanny, especially in support contexts where prior interactions are visible in the same thread. A 30-token paraphrase pass on the cached answer (using a 1B-parameter model) restores the conversational feel at negligible cost.

In [7]rewrite step
rewriter = LLM(model="meta-llama/Llama-3.2-1B-Instruct",
               enable_prefix_caching=True, gpu_memory_utilization=0.10)

REWRITE_PROMPT = """You will be given a question and a draft answer.
Lightly rephrase the answer so it reads naturally for the question.
Preserve every fact and every number. Do not add information.

Question: {q}
Draft: {a}
Rewritten:"""

def rewrite(q, a, sp=SamplingParams(max_tokens=180, temperature=0.4)):
    p = REWRITE_PROMPT.format(q=q, a=a)
    return rewriter.generate([p], sp)[0].outputs[0].text.strip()

sample_q = "how long until my refund hits my account?"
sample_a = ("Refunds are issued to the original payment method and typically "
            "appear within 5–7 business days, depending on your bank.")

print(rewrite(sample_q, sample_a))
Refunds go back to the card you originally paid with, and they usually land in your account within 5 to 7 business days. The exact timing depends on your bank.

I evaluated factual preservation by re-running the verifier on (cached answer, rewritten answer) and confirming the equivalence label held in 99.4% of cases. The 0.6% failures were almost all numeric drift, which I now block by lightly post-processing the rewrite to copy any numeric tokens verbatim from the source.

Putting It Together

Here is the full pipeline as I run it. Every stage has an early-exit; the LLM call only happens for queries that pass all four cache stages without a hit.

In [8]end-to-end pipeline
import redis
kv = redis.Redis()        # exact-match store
ann = index               # embedding index from cell [1]
answers = {}              # qhash -> (q_text, answer_text)

def serve(q: str):
    h = qhash(q)

    # 1. exact match
    if h in answers:
        q_c, a_c = answers[h]
        return rewrite(q, a_c), "exact"

    # 2. embedding candidate
    e = encoder.encode([q], normalize_embeddings=True).astype("float32")
    D, I = ann.search(e, 1)
    sim, idx = float(D[0, 0]), int(I[0, 0])
    if sim >= 0.83:
        q_c, a_c = list(answers.values())[idx]
        # 3. verifier
        if verify(q, q_c, a_c):
            return rewrite(q, a_c), "embed+verified"

    # 4. LLM call (with prefix cache active)
    out, _ = call(q)
    a = out.outputs[0].text.strip()
    answers[h] = (q, a)
    # also push embedding into ANN
    ann.add(e)
    return a, "miss"

# replay the workload
buckets = {"exact": 0, "embed+verified": 0, "miss": 0}
t0 = time.perf_counter()
for q in queries.text:
    _, src = serve(q)
    buckets[src] += 1
elapsed = time.perf_counter() - t0

print(f"served {len(queries):,} queries in {elapsed:.1f}s")
for k, v in buckets.items():
    print(f"  {k:<16} {v:5d}  ({v/len(queries):.1%})")
served 5,000 queries in 318.4s exact 1103 (22.1%) embed+verified 1612 (32.2%) miss 2285 (45.7%)

54% of traffic served without a model call. Add the prefix-cache speedup on the remaining 46% and the total compute savings are larger than the hit rate alone suggests.

The Numbers That Actually Matter

I instrumented the pipeline with three counters: GPU-seconds spent in prefill, GPU-seconds spent in decode, and CPU-seconds spent in the verifier and rewrite. Comparing the hybrid stack against a baseline (no cache, no prefix sharing) on the same 5,000-query workload:

58.8% reduction in total compute. p50 latency drops by an order of magnitude because half the traffic short-circuits to a cache hit; p95 still benefits substantially from the prefix cache on the misses. The wrong-answer rate ticks up by 0.2 percentage points, which is the verifier's residual false-positive rate flowing through to served answers: a deliberate, measured tradeoff.

The conceptual point: we are not caching the model's final output and praying it applies to the next user. We are caching computations (prefill activations, candidate retrievals, verifier decisions) and recomposing them per request. Final-output caching has a hit-rate ceiling and a quality floor. Computation caching scales with prefix overlap and degrades gracefully.

What Breaks This

I want to be honest about where the hybrid stack stops working.

High personalisation. If every answer needs to reference user-specific account state, the verifier will (correctly) reject most embedding candidates because the cached answer doesn't apply to the new user. You're left with the prefix cache only, which is still worth doing (Anthropic's prompt-caching API alone routinely cuts costs by 40–60% on long-context agentic workloads), but the embedding stage adds little.

High temporality. Workloads where answers go stale within hours (live status, prices, inventory) need a TTL on the embedding cache and a freshness check before the verifier runs. I keep TTLs short and use the cache primarily for "evergreen" intents.

Tool-using agents. When the LLM call triggers tool invocations whose results vary per request, you can still cache the prefix and the planning step, but you cannot cache the post-tool answer. The hybrid stack becomes "prefix cache + planning cache" and the embedding/verifier stages move to the planner output rather than the final response.

Adversarial inputs. The verifier is a model and can be fooled. I run an offline red-team suite weekly that mines for inputs where the verifier disagrees with a stronger judge model, and feed those into the next training round. This is a continuous process, not a one-time evaluation.

The Build Order, If You're Starting Today

  1. Turn on prompt/KV caching in your inference stack: vLLM's --enable-prefix-caching or the equivalent API setting. This is one config flag and is essentially free.
  2. Add an exact-match cache with normalisation. A few hours of work, recovers the long tail of duplicates.
  3. Build an evaluation set of 500–1,000 labelled (query, query, equivalent?) pairs. You cannot tune anything downstream without it.
  4. Add the embedding ANN as a candidate generator at a recall-tuned threshold. Do not serve directly from this stage.
  5. Train or fine-tune a small cross-encoder verifier. A MiniLM-class model on a few thousand labelled pairs is enough.
  6. Add the rewrite step only after you've shipped the cache for a week and looked at user complaints. If nobody notices the verbatim cached answers, skip it.

The order matters. Most teams I've seen start with semantic caching, get burned by false positives, and conclude that caching doesn't work for LLMs. It does, just not the way the slide deck suggested. Cache the computations, verify before you serve, and the 60% efficiency win is real.
