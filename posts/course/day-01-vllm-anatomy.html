The Three Loops in vLLM

Hold three loops in your head simultaneously. Most operational confusion about vLLM comes from conflating them.

The HTTP loop in vllm/entrypoints/openai/api_server.py accepts requests, converts them to SamplingParams, and pushes them onto the engine's input queue. It also streams tokens out of the engine and back to the HTTP client. It does no scheduling and no inference. This is uvicorn-shaped asyncio.

The engine loop in vllm/engine/llm_engine.py drives LLMEngine.step() in a tight while-True. Each step is one iteration of continuous batching: the scheduler decides which requests run this step, the model runner executes one forward pass on whatever batch the scheduler returned (prefill chunks plus decodes), and the sampler turns logits into tokens. This is the loop where p99 lives.

The worker loop in vllm/worker/worker.py is the per-GPU process that owns the model weights and the KV-cache memory pool. With tensor parallelism >1 there is one worker per rank, coordinated by Ray or the multiproc executor. The worker's execute_model is what actually moves tensors on the GPU.

The boundary between these loops is the part of the architecture nobody draws on whiteboards. Most performance problems live on the boundary: queueing between HTTP and engine, prefill-decode interference inside the engine step, all-reduce stragglers between workers. The diagram below is the one I keep on a sticky note.

One Engine Step, in Source-Level Detail

Open vllm/engine/llm_engine.py and find LLMEngine.step(). The shape of it is unchanged across recent minor versions even if call sites move. The four moves are:

  1. Schedule. The scheduler decides which sequences run this step and what shape the batch is (how many prefill chunks, how many decodes, and the KV blocks each one will read or write).
  2. Execute. The worker runs a single forward pass on the batch the scheduler chose, then samples one token per sequence.
  3. Update. Sequences advance: prefill chunks consume part of the prompt, decoded tokens append to their KV state, finished sequences are removed.
  4. Emit. Outputs (sampled tokens, finished sequences, logprobs) go onto the output queue for the HTTP loop to stream.

The scheduler is the load-bearing piece. Find vllm/core/scheduler.py and the method Scheduler.schedule(). Its job is to take the current set of waiting sequences (not yet started prefill) and running sequences (mid-generation) and pack a batch that fits in the KV budget and the token budget for this step. Two budgets, not one.

The KV budget is the number of free blocks in the block manager. Each prefill chunk needs ceil(chunk_tokens / block_size) new blocks; each decode step needs zero or one new block depending on whether the existing last block has room. If the budget is exhausted, the scheduler swaps a running sequence out (its blocks go to CPU; reverse on resume) or pre-empts it (its blocks free; the sequence restarts from the prompt). Both are expensive. Swap is bounded by PCIe bandwidth; pre-emption is bounded by re-doing prefill.

The token budget is max_num_batched_tokens. This is the per-step compute budget; the forward pass operates on this many tokens of prefill plus decode combined. If you set it small you bound prefill chunk size and inter-token latency stays low; if you set it large you front-load prefill cost and time-to-first-token improves at the expense of decodes already running.

The relationship between these two budgets and your traffic is where p99 dies.

Continuous Batching, Chunked Prefill, and Why Both Exist

Continuous batching means the batch composition can change every step. A new request that arrives at step N joins the batch at step N+1 (or N+2 if scheduling is delayed). A finished request leaves immediately. The model runs on whatever sequences are alive that step.

The naive version of this puts pure-prefill steps and pure-decode steps in alternation. When a long prompt arrives, prefill takes a whole step (sometimes many steps if it cannot fit), and during those steps your already-decoding sequences are paused. Their inter-token latency (ITL) spikes. From the outside, every user with a streaming response sees a stutter.

Chunked prefill solves this. Instead of putting a 4096-token prefill into one batch, the scheduler splits it into chunks of max_num_batched_tokens minus the decode tokens already in-flight, and feeds one chunk per step alongside the decodes. The decode latency is preserved at the cost of slightly higher time-to-first-token for the prefilling request.

Read vllm/core/scheduler.py for the chunked-prefill logic. The key variable is SchedulerConfig.chunked_prefill, which is on by default in 0.7.x for most model configs. The chunk size adapts: it is max_num_batched_tokens - num_running_decode_tokens. When you have many decodes in flight, prefill chunks get small; when you have few, they get large. This is the right behaviour but it has a failure mode covered in Lab 5.

The mental model I use for chunked prefill: each step is a fixed compute budget (max_num_batched_tokens). The scheduler fills the budget with decodes first (they are cheap, one token each), then uses the remainder for prefill chunks. If decodes alone exceed the budget, no prefill happens that step. This is why a flood of long-context decodes can starve new requests of prefill.

Where p99 Actually Dies

Three places, each of which corresponds to a specific source-level mechanism. Internalise these because every operational fix you will make is some variation of recognising which of the three is happening.

1. Pre-emption thrashing under KV pressure

When the block manager runs out of free blocks, the scheduler picks a victim sequence and pre-empts or swaps it. The default policy is last-come-first-pre-empted for fairness, but the cost falls on a running user who was about to finish. Read Scheduler._preempt. The smoking gun in your logs is a "Preempting" line; the smoking gun in a metric is vllm:num_preemptions_total climbing.

Pre-emption is much more expensive than its name suggests. A pre-empted sequence loses its KV state. When it resumes, vLLM re-prefills its entire prompt. For a 4k-token prompt that you have already paid for once, you pay again. Under heavy load, a fraction of requests can be pre-empted multiple times and re-prefilled each time, and their tail latency is dominated by this re-do work, not by the model.

2. Prefill-decode interference under chunked prefill misconfiguration

The default max_num_batched_tokens in vLLM 0.7.x is 2048 unless you override it. On an H100 serving Llama-3.1-8B, the GPU can prefill substantially more than 2048 tokens per step. If you have a long-context workload (think 16k-32k prompts), with the default setting prefill takes 8 to 16 steps per request. During those steps, decodes in flight get slow because every step pays prefill-shaped cost.

Bumping max_num_batched_tokens to 8192 or 16384 improves prefill throughput at the cost of decode ITL: the per-step time grows because each step is doing more work. There is no single right answer; the right answer depends on the prefill-to-decode ratio of your workload. Lab 3 will make you measure this on a real distribution.

3. Scheduler starvation under priority inversion

Default vLLM has no priority. All requests are equal, scheduled FIFO. This is fine for symmetric workloads and catastrophic for asymmetric ones. A single 32k-prompt request can monopolise the prefill budget for many steps, during which new short requests sit in the waiting queue. The TTFT of the short requests goes to seconds even though their compute requirement is trivial.

The fix is a priority class on the scheduler. You will build this in Lab 4. There is a community PR (#7568, others) for this; the lab walks you through a minimal version that you understand line-by-line.

Sampling, Briefly

The sampler in vllm/model_executor/layers/sampler.py is much simpler than the scheduler. It takes the model's last-layer logits, applies temperature, top-k, top-p, repetition penalties, optional structured-output constraints (Outlines, XGrammar, lm-format-enforcer), and returns one token per sequence. The work is almost all element-wise on the logits tensor; on H100 it costs a few hundred microseconds per step regardless of batch size.

There is one performance trap: logits processors that fall back to CPU. Structured-output libraries sometimes mask logits on CPU and copy back. If you have a workload where every request uses JSON-grammar constraints, profile this carefully. The fix is usually to use xgrammar, which keeps masks on the GPU.

Lab 02 ~60 min

Instrument the engine loop and the scheduler

Patching. Difficulty: medium. Output: per-step trace with phase breakdown.

Add explicit timing around the four moves of step(). Write each measurement to a file or a Prometheus pushgateway. You want, per step:

  • t_schedule_us: time spent inside schedule()
  • t_exec_us: time spent inside execute_model()
  • t_process_us: time in _process_model_outputs()
  • n_prefill_tokens, n_decode_tokens, n_waiting, n_running, n_swapped
  • n_preemptions_this_step (count of Preempting log lines)

The cleanest place to patch is step() itself. Wrap each section in time.perf_counter_ns() and append to a list that you flush every 100 steps.

patch.pyminimal monkey-patch for in-place instrumentation
import time, json, os
from vllm.engine.llm_engine import LLMEngine

_orig_step = LLMEngine.step
_buf = []

def step_instrumented(self):
    t0 = time.perf_counter_ns()
    sched_meta, sched_out, _ = self.scheduler[0].schedule()
    t1 = time.perf_counter_ns()

    if not sched_out.is_empty():
        outs = self.model_executor.execute_model(
            execute_model_req=self._prepare_request(sched_out, sched_meta))
        t2 = time.perf_counter_ns()
        processed = self._process_model_outputs(outs, sched_out)
        t3 = time.perf_counter_ns()
    else:
        t2 = t3 = t1
        outs, processed = [], []

    _buf.append({
        "t_schedule_us":   (t1 - t0) / 1e3,
        "t_exec_us":       (t2 - t1) / 1e3,
        "t_process_us":    (t3 - t2) / 1e3,
        "n_prefill_tokens": sum(g.token_chunk_size for g in sched_out.prefill_seq_groups),
        "n_decode_tokens":  len(sched_out.decode_seq_groups),
        "n_waiting":  len(self.scheduler[0].waiting),
        "n_running":  len(self.scheduler[0].running),
        "n_swapped":  len(self.scheduler[0].swapped),
    })
    if len(_buf) >= 100:
        with open("/tmp/vllm_trace.jsonl", "a") as f:
            for r in _buf: f.write(json.dumps(r) + "\n")
        _buf.clear()
    return processed

LLMEngine.step = step_instrumented

Note this is a teaching-grade patch; the production version checks sched_out.is_empty() correctly and matches the exact upstream control flow. The point is to demonstrate the technique, then port it cleanly into a forked branch.

Lab 03 ~90 min

Poisson load generator with realistic prompt distribution

Load testing. Difficulty: medium-hard. Output: TTFT, ITL, throughput across two knob sweeps.

The default vLLM benchmark scripts are fine for sanity but they are not what you measure with. You need a workload that has the shape of your traffic: a heavy-tailed prompt-length distribution, a Poisson arrival process, and a mix of prefill-bound and decode-bound requests.

Build a generator. Sample prompt lengths from a log-normal with mean 800 tokens and sigma 1.2 (this matches a typical chat-plus-code workload). Sample arrival times from an exponential distribution to get Poisson arrivals. Fix max_tokens at 256 for decoding parity.

loadgen.pyPoisson arrivals, log-normal prompts
import asyncio, aiohttp, math, random, time, json, os
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained(os.path.expanduser("~/models/llama-3.1-8b"))
TARGET = "http://localhost:8000/v1/completions"

# Pre-sample a pool of natural prompts of varying lengths.
# Use the first N tokens of a public corpus (your choice; use what you have).
def make_prompts(n=2000):
    base = open("the-pile-sample.txt").read()
    toks = tok.encode(base)
    out = []
    for _ in range(n):
        L = max(32, min(8000, int(random.lognormvariate(math.log(800), 1.2))))
        start = random.randrange(0, max(1, len(toks) - L))
        out.append(tok.decode(toks[start:start + L]))
    return out

async def fire(session, prompt, qps, results):
    t_send = time.perf_counter()
    async with session.post(TARGET, json={
        "model": os.path.expanduser("~/models/llama-3.1-8b"),
        "prompt": prompt, "max_tokens": 256, "temperature": 0.0,
        "stream": True,
    }) as r:
        ttft = None; n_tok = 0; t_prev = t_send
        itl = []
        async for line in r.content:
            if line.startswith(b"data: "):
                if ttft is None:
                    ttft = time.perf_counter() - t_send
                else:
                    itl.append(time.perf_counter() - t_prev)
                t_prev = time.perf_counter(); n_tok += 1
        results.append({"ttft": ttft, "itl_p50": sorted(itl)[len(itl)//2] if itl else None,
                        "itl_p99": sorted(itl)[int(len(itl)*0.99)] if itl else None,
                        "n_tok": n_tok, "elapsed": time.perf_counter() - t_send})

async def run(rps, duration_s):
    prompts = make_prompts()
    results = []
    async with aiohttp.ClientSession() as s:
        t0 = time.perf_counter()
        tasks = []
        while time.perf_counter() - t0 < duration_s:
            tasks.append(asyncio.create_task(
                fire(s, random.choice(prompts), rps, results)))
            await asyncio.sleep(random.expovariate(rps))
        await asyncio.gather(*tasks)
    return results

if __name__ == "__main__":
    import sys
    rps = float(sys.argv[1]); dur = int(sys.argv[2])
    res = asyncio.run(run(rps, dur))
    with open("loadgen_out.jsonl", "w") as f:
        for r in res: f.write(json.dumps(r) + "\n")

Lab 04 ~120 min

Patch the scheduler with a priority class

Patch upstream-quality. Difficulty: hard. Output: forked branch with priority-aware scheduling and measured tail-latency improvement.

The default FIFO scheduling produces priority inversion under asymmetric load. You will add a priority: int field to SamplingParams, plumb it to the scheduler, and change schedule() to prefer higher-priority sequences when admitting from the waiting queue.

The minimum diff touches three files:

  • vllm/sampling_params.py: add priority: int = 0 to SamplingParams
  • vllm/engine/protocol.py or the OpenAI server: accept a x-vllm-priority header and pass it through
  • vllm/core/scheduler.py: when popping from self.waiting, sort by (-priority, arrival_time)

The non-trivial part is the sort. The default self.waiting is a deque (FIFO). You can either keep a deque and sort on-admission (cheap if waiting is small), or switch to a heap keyed by (-priority, arrival_time). The heap is cleaner; do that.

scheduler.py (sketch)priority-aware admission
import heapq

class Scheduler:
    def __init__(self, ...):
        ...
        # Replace `self.waiting: Deque[SequenceGroup]` with a heap.
        # Each item is (-priority, arrival_ns, sg_id, sequence_group).
        self.waiting_heap: list = []

    def add_seq_group(self, seq_group):
        prio = seq_group.sampling_params.priority
        heapq.heappush(self.waiting_heap,
                       (-prio, seq_group.arrival_time, id(seq_group), seq_group))
        # Keep self.waiting (or its analogue) in sync for any code that
        # iterates it for stats; the heap is the source of truth.

    def _schedule_prefills(self, ...):
        admitted = []
        while self.waiting_heap and budget.remaining_tokens > 0:
            _, _, _, sg = heapq.heappop(self.waiting_heap)
            if not self._can_allocate(sg, budget):
                # Put back, stop trying lower-priority items.
                heapq.heappush(self.waiting_heap, (-sg.sampling_params.priority,
                                                   sg.arrival_time, id(sg), sg))
                break
            self._allocate(sg)
            admitted.append(sg)
            budget.consume(sg)
        return admitted

Write a test workload: 90% of requests at priority 0 with 4k-token prompts, 10% at priority 10 with 256-token prompts. Run with the patched scheduler and again with stock vLLM. Plot TTFT-p99 for the high-priority cohort across the two configurations. You should see a substantial improvement for the high-priority requests; the low-priority cohort's TTFT-p99 will get slightly worse, which is correct, that is what priority means.

Lab 05 ~90 min

Find a real chunked-prefill failure mode and reproduce it

Adversarial workload construction. Difficulty: hard. Output: a workload that demonstrates the failure plus a one-line config change that mitigates it.

Chunked prefill has a known weakness: when many decodes are in flight, the chunk size shrinks toward zero and the scheduler effectively stalls prefill. This is the right behaviour in steady state but it produces head-of-line blocking when a single new long prompt arrives during a busy decode period.

Construct the workload that triggers this. Send 128 concurrent requests of 4096 tokens prompt and 1024 tokens output (these will sit in decode for a while). At T = 30s, send one request with a 16k-token prompt and 64-token output. Measure that one request's TTFT.

You should observe TTFT well above what a 16k prefill should cost on an idle H100. Use the instrumentation from Lab 2 to see why: the prefill chunk size during those steps is the budget minus the 128 decodes (each one token), and the budget at default is 2048. So each step prefills 2048-128 = 1920 tokens; 16384/1920 = nine steps minimum, with the decode-shaped per-step time.

Mitigations:

  • Bump max-num-batched-tokens to 16k+ so the long prefill fits in one chunk. This raises ITL for the concurrent decodes.
  • Use the priority patch from Lab 4 to admit the new request ahead of the decodes for one full step.
  • Disable chunked prefill (--enable-chunked-prefill=False) and accept ITL spikes during prefill.

None of these is universally right. The point of the lab is to recognise that the "right" setting is workload-dependent and you can only choose it after measurement.

What You Should Take Away

vLLM is three loops on a shared queue. The HTTP loop is asyncio shape. The engine loop is sync, single-threaded, and runs the scheduler plus executor plus output processor. The worker loop is per-GPU. Most operational confusion conflates these.

The engine step is a two-budget bin-packing problem. The KV budget (free blocks) governs how many sequences can be alive. The token budget (max_num_batched_tokens) governs how much work fits in a forward pass. Most knob choices are choosing which budget to be tight on.

Pre-emption is much more expensive than its name. Pre-empted sequences re-prefill on resume. Under load this is a self-reinforcing failure mode: pre-emptions consume capacity, which causes more pre-emptions. Watch the metric.

Chunked prefill is the right default but it has a head-of-line failure mode. Lab 5 reproduces it. Recognising it in production logs is a skill; you now have it.

Priority is missing from stock vLLM for a reason. It requires careful design choices about pre-emption and admission, and the upstream maintainers have not landed a canonical version. Your Lab 4 patch is a starting point, not a finished feature.
