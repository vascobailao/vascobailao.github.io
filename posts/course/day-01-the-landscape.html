The Landscape: How Modern AI Coding Tools Actually Work

May 15, 2026 ~90 min including labs 5 labs
Course Copilot Cursor Claude Code Cody Continue Aider

Day 1 is intentionally a survey day. The mistake people make at the start of any AI tooling journey is to pick the most-marketed product and conclude that what it does is what AI coding tools do. The reality is that the seven major tools differ on almost every axis that matters: the interaction surface, the underlying model, the context they have access to, the deployment model, the latency budget, the kinds of tasks they are designed to handle. By the end of today you will have all seven (or as many as you can install in 90 minutes) running on your machine, and a personal opinion grounded in actual use rather than vendor copy.

This is the day where most people unlearn the most. The "AI coding tool" category is not one thing. It is at least three things, possibly five, and conflating them is the source of about 80% of the bad takes you will read about whether AI is helping engineers ship.

The Three Modes

Almost every AI coding tool currently shipping is one of three architectural shapes. A few are hybrids. None of them are doing magic; they are doing different things at different speeds with different scopes.

Mode 1: Inline completion (autocomplete on steroids)

The original AI coding interaction. You type, the model predicts the next chunk of code, you accept or reject with a key. The model sees a window of code around your cursor (the prefix and a small amount of the suffix), and produces a continuation. The interaction is sub-second, the cognitive cost is essentially zero (you tab or you keep typing), and the failure mode is that you accept code you did not actually want.

Tools in this mode: GitHub Copilot (the original), Tabnine, Codeium, Continue (open-source, can be self-hosted), Supermaven, Cursor's tab-completion mode. The underlying technique is fill-in-the-middle (FIM), which we will dissect in detail on Day 3.

What this mode is good at: typing less for code that follows obvious patterns. Repetitive boilerplate. The next line of a clear sequence. Property access. Familiar idioms in a language you know.

What this mode is bad at: any task that requires understanding more than the local file. Architectural decisions. Anything where the right answer depends on code you have not opened recently. Refactors that span multiple files.

Mode 2: Chat side-panel (a colleague at your desk)

You ask a question, the model answers, optionally with a suggested edit you can apply. The interaction is multi-second, the model has access to whatever you @-mention or paste, and the failure mode is that the answer looks correct but does not work in your specific context.

Tools in this mode: Copilot Chat, Cursor's chat panel, Cody Chat (Sourcegraph), Continue's chat, JetBrains AI Assistant. The model is bigger than the inline-completion model and the latency budget is correspondingly larger.

What this mode is good at: "how do I do X with library Y?" "what does this function do?" "rewrite this in TypeScript." Targeted single-file edits. Explanations.

What this mode is bad at: tasks that require touching many files coherently. Tasks where the model needs to discover what it does not know. Anything you cannot fit in the context window manually.

Mode 3: Agentic (a colleague who can run things)

You describe a goal, the model plans, executes (running shell commands, reading files, writing files, running tests), observes the results, and iterates until the goal is met or it gives up. The interaction is multi-minute, the model has tool access, and the failure mode is that it confidently completes the wrong task or burns through your token budget on a doomed approach.

Tools in this mode: Claude Code, Cursor Agent (Composer), Aider, Cline (the open-source VS Code extension), OpenAI Codex CLI, Goose, Devin and other autonomous agent products. This is the mode that is changing fastest and the mode where the product UX matters most because you are reviewing diffs rather than typing characters.

What this mode is good at: multi-file refactors. End-to-end feature implementation in well-tested code. Tasks where the spec is clear and the verification loop is fast (tests run in seconds, not minutes). Migration work.

What this mode is bad at: tasks where the spec is ambiguous and the model has to guess. Codebases without good tests. Anything where you do not have time to review carefully (the speed at which agents produce diffs exceeds the speed at which most humans can review them, which is its own problem).

The principle behind the labs that follow: you cannot pick tools well without using them on tasks that resemble your real work. Vendor demos are curated. Your codebase is not. Today's labs make you generate your own evidence.

Setup You Need Before the Labs

You will need:

  • A laptop with at least 16GB RAM. More if you are going to run a local model.
  • VS Code installed (most extensions live there; even if you prefer JetBrains, install VS Code as a second editor for this course).
  • Node.js 20+ and Python 3.11+.
  • A small open-source repo to experiment in. Clone fastapi/fastapi if you want a Python target, or expressjs/express if you prefer Node. Anything around 50k lines of real code will do.
  • A free GitHub account (Copilot has a free tier for non-students as of late 2025).
  • A Cursor account (free tier available).
  • A Claude.ai account with API access enabled (the free tier of the web product is fine for some labs; Claude Code needs API credits, budget $5 to be safe).
  • A terminal you are comfortable in.

If your employer's policy prevents you from using cloud-hosted tools on company code, do every lab in this course on a personal scratch repo. The point is to learn the tools, not to leak your codebase.

The Labs

Each lab below is independently runnable. They build a portfolio of evidence about which tools work for you. Do not skip the deliverables; they are the point.

Lab 01 ~25 min

Install three tools and confirm they work

Tools: Copilot, Cursor, Claude Code · Difficulty: easy

Get three different tools installed and able to make a successful call against your test repo. The point is not to use them yet; it is to surface installation friction (which is itself a signal about how the tool will fit into your workflow).

Step 1: GitHub Copilot in VS Code

  1. Install the GitHub Copilot extension and the Copilot Chat extension from the VS Code marketplace.
  2. Sign in with the account that has Copilot enabled.
  3. Open a Python file in your test repo. Type def hello_world(): and a newline. Confirm a ghost-text suggestion appears within a second.
  4. Open Copilot Chat (Ctrl+Alt+I or Cmd+Shift+I), ask "what does this file do?" with the current file as context. Confirm you get a coherent answer.

Step 2: Cursor

  1. Download Cursor from cursor.com. It is a fork of VS Code, so your settings can be imported.
  2. Sign in. Open the same test repo.
  3. In the chat panel (Cmd+L), ask the same "what does this file do?" question. Note the difference in response style and speed.
  4. Open Composer (Cmd+I), give it a small task ("add a docstring to every function in this file"). Confirm the diff preview shows up.

Step 3: Claude Code

# macOS / Linux

# launch in your test repo
cd ~/code/fastapi

# inside Claude Code, try:

Confirm the response includes specific test names from the file. If it does not, your API key is not set or the working directory is wrong; re-run.

Deliverable

A note in your course journal listing: total install time per tool, friction encountered, and your first-impression rating (1 to 5) of each tool's onboarding. Be honest; this is the only data you will have when picking tools later.

Lab 02 ~20 min

Run the same task across all three tools

Difficulty: easy · Generates the first comparison data

Pick a real task that does not require deep codebase knowledge: "add a function parse_iso8601(s: str) -> datetime that parses an ISO-8601 string and raises ValueError on malformed input. Include a unit test." Run this exact prompt in all three tools, against an empty file in your test repo.

Score each result on:

  • Correctness: does the code work as specified?
  • Coverage: does the unit test cover the malformed-input case?
  • Style: does it match the existing codebase's conventions (typing style, docstring format, test framework)?
  • Latency: wall-clock seconds from prompt sent to acceptable diff in front of you.

Pay particular attention to whether each tool noticed the existing test framework in the repo. Copilot Chat will often guess unittest by default; Cursor's Composer and Claude Code should pick up pytest because they have repo-wide context.

Deliverable

A markdown table in your journal with the four scores per tool. This is your first data point on a question you will keep answering for the rest of the course: which tool is the right one for which task?

Lab 03 ~15 min

Measure inline-completion latency rigorously

Difficulty: medium · Tools: Copilot, Cursor (tab), optionally Continue · Reveals how much sub-second-ness you actually get

Inline completion is the mode that lives or dies on latency. A 200ms ghost text feels magical; a 700ms ghost text feels broken. Most teams have never measured this on their actual workload.

Lab 04 ~20 min

Probe each tool's context strategy

Difficulty: medium · Reveals what the tool actually sees

Models do not "know your codebase." They know whatever the tool put in their context window. The difference between tools is mostly the difference in context strategy. This lab makes that visible.

Pick a function in your test repo that is called by exactly one other function elsewhere in the codebase. Open the file containing the called function. Now ask each tool: "Where in the codebase is this function called from? Quote the calling line."

The pattern of correct answers tells you what each tool's retrieval looks like:

  • Copilot Chat with the @workspace mention has a chance; without it, very low chance.
  • Cursor's chat with no @-mentions will sometimes get it via its background indexing; with @codebase it should reliably succeed.
  • Claude Code typically gets it because it can run grep as a tool call and find the answer that way.
  • Continue with no embeddings configured will fail; with embeddings, it depends on the configuration.

Try also asking: "Summarise every place in the codebase where authentication is checked." This is a multi-hop retrieval question and is much harder. Note which tools attempt actual repo search and which ones hallucinate plausibly-named files that do not exist.

Deliverable

A short note per tool: does it have repo-wide retrieval, and is it on by default? This is the single most important property to know about a tool, and most documentation is unclear about it.

Lab 05 ~10 min · capstone for Day 1

Build your personal scoring rubric

Difficulty: easy · Most useful artifact of the day

Take everything you have noticed in Labs 1 to 4 and write down the rubric you will use to evaluate every AI coding tool from now on. The rubric is personal; what matters is that it is explicit. A reasonable starting template:

rubric.mdpersonal scoring rubric
# My AI coding tool rubric

Score each axis 1 to 5. Total out of 35. I will not adopt a tool below 22.

1. **Latency for inline completion** (median over my benchmark prompts).
   1: >1s, painful. 5: <200ms, invisible.

2. **Repo-wide retrieval quality** (Lab 04 questions).
   1: hallucinates files. 5: cites real call sites every time.

3. **Style match to my codebase** (does the output blend in?).
   1: ignores conventions. 5: indistinguishable from my code.

4. **Diff review UX** (when it produces multi-file changes, can I review them sanely?).
   1: dumps text. 5: structured diffs with explanations.

5. **Failure recovery** (what happens when a command fails, a test breaks, an import is wrong?).
   1: gives up or loops. 5: diagnoses and proposes a real fix.

6. **Friction cost** (install, login, daily startup, license).
   1: enterprise-only with a long onboarding. 5: install and go.

7. **Data posture** (does my code leave my machine? where? for how long?).
   1: opaque cloud-only. 5: self-hostable with audit logs.

What You Should Take Away

Five things, regardless of which tools you ended up liking.

The category is not one thing. Inline completion, chat, and agents are different products that happen to share a model under the hood. Conflating them produces bad takes (e.g., "AI coding tools cannot do real refactors" is true of inline completion and false of agents).

Latency dominates UX in inline mode. A faster, dumber model usually wins inline. A slower, smarter model usually wins in chat and agent modes. There is no single best model across all three.

Context strategy is the single biggest quality lever. The same model with bad context produces hallucinations. The same model with good context (file imports, related files, project conventions, repo-wide retrieval) produces code that blends in. Most of the differentiation between tools is here.

Self-hosting is real but it is not free. The open-source agentic stack we explored a few posts back (Onyx + CrewAI + vLLM) is a real alternative to Cursor and Claude Code, but it requires engineering investment. The trade is data sovereignty and cost predictability versus polish and pace of model improvement.

You need a rubric, not a favourite. Picking a tool because you saw a good demo is how teams end up with three Copilot licenses they do not use. The rubric you wrote in Lab 5 is the artefact that should drive every adoption decision from now on.
