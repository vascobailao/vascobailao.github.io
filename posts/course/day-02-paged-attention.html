Day 1 was the engine. Day 2 is the kernel inside the engine that does the actual work. Reading PagedAttention is the difference between knowing vLLM uses block-based KV and knowing why that costs you a few percent on prefill, why the block size is 16 and not 8 or 32, and why the H100 FlashAttention-2 paged variant lost to vLLM's bespoke CUDA kernel in some regimes until very recently. By the end of today you will have written your own Triton implementation, verified it against a Python reference, profiled it against xformers and FA2 with Nsight Compute, and produced a regime map showing where each kernel wins.

You will not match the production kernels in absolute throughput. That is fine and expected: the production kernels have years of micro-optimisation, manually tuned MMA tiles, and warp specialisation. Your Triton kernel will be 0.5 to 0.9x of FA2 on most regimes and will beat FA2 on at least one regime that we will identify by construction. The point is not to ship your kernel; the point is that by writing it you understand exactly what the production ones do.

Why PagedAttention Exists at All

Standard attention assumes contiguous KV per sequence. A batch of N sequences with maximum context length T uses a tensor of shape [N, H, T, D]. The contiguous layout makes the attention math straightforward: gather Q for the active query positions, dot product against the K of the sequence, softmax, weighted sum with V. FlashAttention-2 is built on this layout.

The problem with contiguous KV in a multi-tenant inference server is fragmentation. Sequences have different lengths. If you allocate T_max tokens per sequence, you waste memory on short sequences. If you allocate just-enough and a sequence grows past its allocation, you have to copy. Either way, you cannot dynamically add or remove sequences from the batch without paying for memory churn. This was the operational reality before vLLM: serving a mixed batch of 50-token and 4000-token sequences meant either reserving 4000 tokens per slot (90% waste on the short ones) or constantly compacting (latency spikes from memcpy).

The PagedAttention paper (Kwon et al., 2023) borrows the idea from operating systems. Memory is allocated in fixed-size blocks (the paper uses 16 tokens, vLLM has used 16 throughout, though it is now configurable). Each sequence has a block table: a small array mapping its logical token positions to the physical blocks that hold its KV. Sequences can grow by appending blocks. Sequences can be freed by releasing blocks back to the pool. Two sequences can share blocks if they share a prefix (this is the foundation of prefix caching).

memory layoutcontiguous vs. paged
Contiguous KV (FA2 layout)
  K_cache:  [num_seqs, num_heads, max_seq_len, head_dim]
              ^                       ^
              |                       wasted on short seqs
              free per-seq view: K_cache[seq_idx]  ->  one contiguous chunk

Paged KV (vLLM layout)
  K_cache:        [num_blocks, num_kv_heads, block_size, head_dim]
                    ^
                    physical block pool, shared across all sequences

  block_tables:   [num_seqs, max_blocks_per_seq]
                    ^
                    logical -> physical block mapping

  context_lens:   [num_seqs]
                    ^
                    actual length per sequence (in tokens)

To read seq s, position p:
  block_logical = p // block_size
  block_offset  = p % block_size
  block_phys    = block_tables[s, block_logical]
  k             = K_cache[block_phys, kv_head, block_offset, :]

The kernel pays for this in two ways. First, the gather pattern: each block load is at a different physical address determined by block_tables, so the memory access is not strictly sequential. The hardware tolerates this well because block_size=16 and head_dim=128 give a 16x128xsizeof(fp16) = 4KB load per block, which is well-aligned and large enough to amortise the address indirection. Second, the loop over blocks pays an extra load per block (the block_tables entry). On H100 this is a few clocks per block, negligible.

The kernel saves on this in one big way: no padding. The contiguous layout pads to max_seq_len; the paged layout uses exactly ceil(context_len / 16) blocks per sequence. For mixed workloads, the memory savings are large enough that you can hold more sequences live, which often beats the per-kernel overhead by a substantial margin.

The Online Softmax Recap

You need this to write the kernel. If you have read the FlashAttention-2 paper, skip ahead.

Attention computes O = softmax(QK^T / sqrt(d)) V. The softmax is the bottleneck because it requires reading all of QK^T to normalise. The FlashAttention trick is online softmax: process K and V in blocks, maintain a running max m and a running sum l, and rescale the accumulated output when a new max is found.

Pseudocode, for one query and N blocks of K and V:

algorithmonline softmax in one query
m = -inf
l = 0
acc = 0    # head_dim vector

for each KV block of size B:
    s = q @ k_block.T          # shape [B]
    m_new = max(m, max(s))
    alpha = exp(m - m_new)     # rescale factor for old acc
    p = exp(s - m_new)         # softmax numerator for this block
    l = l * alpha + sum(p)     # new denominator
    acc = acc * alpha + p @ v_block   # accumulate
    m = m_new

return acc / l

Three things to internalise from this. The alpha rescaling makes the accumulator correct when a new max is discovered, by retroactively adjusting the contribution of earlier blocks. The pass is one-shot per block, so the kernel never materialises the full QK^T matrix. And the per-block math is what your Triton kernel will look like, almost line for line.

The Triton Kernel, in Pieces

You will build the kernel in stages. The first version is decode-only: one query token per sequence, which is the common case for inference once prefill is done. The grid is (num_seqs, num_q_heads): one program per (sequence, head) pair, parallelising across the batch. Each program loops over the KV blocks of its sequence and accumulates the output for that one query.

The kernel signature is large but every argument has a purpose. The strides handle non-contiguous tensors (which happen the moment you slice or transpose). Block size and head dim are tl.constexpr because Triton specialises kernels by their constexpr values and you want the loop bounds known at compile time.

paged_attn_v1.pydecode kernel, one query per seq
import torch, triton, triton.language as tl

@triton.jit
def paged_attn_decode_kernel(
    Q_ptr, K_cache_ptr, V_cache_ptr,
    block_tables_ptr, context_lens_ptr,
    Out_ptr, scale,
    # Q strides
    q_stride_s, q_stride_h, q_stride_d,
    # K/V cache strides
    kv_stride_blk, kv_stride_h, kv_stride_t, kv_stride_d,
    # block_tables strides
    bt_stride_s, bt_stride_b,
    # Out strides
    o_stride_s, o_stride_h, o_stride_d,
    # constants
    HEAD_DIM: tl.constexpr,
    BLOCK_SIZE: tl.constexpr,
    NUM_KV_HEADS: tl.constexpr,
    NUM_Q_HEADS_PER_KV: tl.constexpr,  # = num_q_heads // num_kv_heads
    MAX_BLOCKS_PER_SEQ: tl.constexpr,
):
    seq_idx = tl.program_id(0)
    q_head_idx = tl.program_id(1)
    kv_head_idx = q_head_idx // NUM_Q_HEADS_PER_KV

    ctx_len = tl.load(context_lens_ptr + seq_idx)
    num_blocks = (ctx_len + BLOCK_SIZE - 1) // BLOCK_SIZE

    # Load this seq/head query into registers
    d_off = tl.arange(0, HEAD_DIM)
    q = tl.load(Q_ptr + seq_idx * q_stride_s
                       + q_head_idx * q_stride_h
                       + d_off * q_stride_d).to(tl.float32) * scale

    # Online softmax state
    m_i = -float('inf')
    l_i = 0.0
    acc = tl.zeros([HEAD_DIM], dtype=tl.float32)

    # Loop over logical blocks
    for blk in range(0, num_blocks):
        phys_blk = tl.load(block_tables_ptr + seq_idx * bt_stride_s
                                            + blk * bt_stride_b)
        # Tokens in this physical block belonging to this seq
        n_tok = tl.minimum(BLOCK_SIZE, ctx_len - blk * BLOCK_SIZE)
        t_off = tl.arange(0, BLOCK_SIZE)
        t_mask = t_off < n_tok

        # Pointer math for K block: [BLOCK_SIZE, HEAD_DIM]
        k_base = (K_cache_ptr + phys_blk * kv_stride_blk
                              + kv_head_idx * kv_stride_h)
        k = tl.load(k_base + t_off[:, None] * kv_stride_t
                           + d_off[None, :] * kv_stride_d,
                    mask=t_mask[:, None], other=0.0).to(tl.float32)

        # Scores for this block: [BLOCK_SIZE]
        s = tl.sum(q[None, :] * k, axis=1)
        s = tl.where(t_mask, s, -float('inf'))

        # Online softmax update
        m_new = tl.maximum(m_i, tl.max(s))
        alpha = tl.exp(m_i - m_new)
        p = tl.exp(s - m_new)
        l_i = l_i * alpha + tl.sum(p)

        # V block load and accumulate
        v_base = (V_cache_ptr + phys_blk * kv_stride_blk
                              + kv_head_idx * kv_stride_h)
        v = tl.load(v_base + t_off[:, None] * kv_stride_t
                           + d_off[None, :] * kv_stride_d,
                    mask=t_mask[:, None], other=0.0).to(tl.float32)

        acc = acc * alpha + tl.sum(p[:, None] * v, axis=0)
        m_i = m_new

    acc = acc / l_i

    tl.store(Out_ptr + seq_idx * o_stride_s
                     + q_head_idx * o_stride_h
                     + d_off * o_stride_d,
             acc.to(tl.bfloat16))


def paged_attn_decode(Q, K_cache, V_cache, block_tables, context_lens, scale):
    num_seqs, num_q_heads, head_dim = Q.shape
    num_kv_heads = K_cache.shape[1]
    block_size = K_cache.shape[2]
    out = torch.empty_like(Q)

    grid = (num_seqs, num_q_heads)
    paged_attn_decode_kernel[grid](
        Q, K_cache, V_cache, block_tables, context_lens, out, scale,
        Q.stride(0), Q.stride(1), Q.stride(2),
        K_cache.stride(0), K_cache.stride(1), K_cache.stride(2), K_cache.stride(3),
        block_tables.stride(0), block_tables.stride(1),
        out.stride(0), out.stride(1), out.stride(2),
        HEAD_DIM=head_dim,
        BLOCK_SIZE=block_size,
        NUM_KV_HEADS=num_kv_heads,
        NUM_Q_HEADS_PER_KV=num_q_heads // num_kv_heads,
        MAX_BLOCKS_PER_SEQ=block_tables.shape[1],
    )
    return out

This is roughly 80 lines of real Triton. Read it twice. Three subtleties worth flagging.

First, the fp32 accumulator is mandatory. Doing the softmax in bfloat16 produces NaNs on any context length above a few thousand because of the exponential blowup. Even mixing the load in bf16 and computing in fp32 is the bare minimum; fp16 accumulation is unsafe.

Second, the loop for blk in range(0, num_blocks) is dynamic (the bound is a runtime value). Triton does not unroll dynamic loops by default. If you want unrolling for a known-small upper bound, you pass MAX_BLOCKS_PER_SEQ as constexpr and write for blk in tl.range(0, MAX_BLOCKS_PER_SEQ, num_stages=2); the num_stages=2 pipelines the load and compute. We use the simpler version above and add pipelining in Lab 4.

Third, the masking inside the block (t_mask) handles the last partial block. Every block except possibly the last has exactly block_size valid tokens. The mask is set to tl.arange(0, BLOCK_SIZE) < n_tok. Off-by-ones in this mask produce wrong outputs without an error message; verify against a reference (Lab 2).

What this kernel does NOT do

It is decode-only. Real prefill, including chunked prefill, has multiple query tokens per sequence. Extending the kernel for that requires either a second grid dimension (one program per query position) or tiling over a query block; Lab 3 walks through this. There is also no causal mask: in decode, the query is always the newest token and attends to everything, so no mask is needed. In prefill, you need to mask out the upper triangle.

It also assumes the data type is bfloat16. vLLM also supports fp16 and fp8 KV; the latter requires separate scale tensors per block and an extra dequantisation step in the load. We handle fp8 KV on Day 4.

Profiling Tools You Will Need

Two tools matter for this day. torch.cuda.Event for wall-clock timing of a kernel under a given input; ncu (Nsight Compute) for per-kernel SM utilisation, memory throughput, and warp-state breakdown. The Triton ecosystem also has triton.testing.do_bench which wraps Event-based timing with warmup and statistics.

bench_template.pystandard timing harness
import torch, triton

def bench(fn, *args, warmup=25, rep=100):
    # do_bench returns time-per-call in milliseconds.
    ms = triton.testing.do_bench(lambda: fn(*args), warmup=warmup, rep=rep)
    return ms

# Example usage

For Nsight Compute, you want to capture exactly one launch of one kernel. The way I do it: wrap the kernel call in torch.cuda.profiler.start() / stop() and run with ncu --target-processes all --launch-skip 5 --launch-count 1 --set full python bench.py. The skip-5 is so you avoid the warmup-pass JIT compile, the count-1 captures one launch in full detail. The output is a roughly 100MB report; open with ncu-ui.

The four Nsight numbers you actually look at on first profile: SM utilisation (target above 60%), DRAM bandwidth (you want this in the 70 to 90% of peak for a memory-bound kernel, which paged attention decode is), achieved occupancy (you want above 0.5), and the warp-state breakdown (Stall LG Throttle and Stall Long Scoreboard tell you you are memory-bound; Stall MIO Throttle tells you the LSU pipe is saturated).

The Labs

Lab 01 ~75 min

Reference implementation in pure PyTorch

Correctness scaffolding. Difficulty: medium. Output: a slow but obviously-correct reference you can verify Triton against.

Before you write a kernel you cannot verify, write the reference. The reference is paged attention in PyTorch operations only, with no kernel calls. It is slow (it materialises the full QK^T) but it is short, readable, and trivially correct. Every Triton kernel you ship will diff against this on a fixed-seed input.

reference.pypaged attention, PyTorch only
import torch
import torch.nn.functional as F

def paged_attn_reference(Q, K_cache, V_cache, block_tables, context_lens, scale):
    """
    Q             : [num_seqs, num_q_heads, head_dim]
    K_cache       : [num_blocks, num_kv_heads, block_size, head_dim]
    V_cache       : [num_blocks, num_kv_heads, block_size, head_dim]
    block_tables  : [num_seqs, max_blocks_per_seq]  int32
    context_lens  : [num_seqs]                       int32
    scale         : float, 1/sqrt(head_dim)
    """
    num_seqs, num_q_heads, head_dim = Q.shape
    num_kv_heads = K_cache.shape[1]
    block_size = K_cache.shape[2]
    q_heads_per_kv = num_q_heads // num_kv_heads

    out = torch.zeros_like(Q)
    for s in range(num_seqs):
        ctx = int(context_lens[s].item())
        # gather K and V for this sequence into a contiguous tensor
        n_blocks = (ctx + block_size - 1) // block_size
        phys = block_tables[s, :n_blocks]                # [n_blocks]
        K_s = K_cache[phys]                              # [n_blocks, KV_H, BS, D]
        V_s = V_cache[phys]
        # collapse blocks
        K_s = K_s.permute(1, 0, 2, 3).reshape(num_kv_heads, n_blocks * block_size, head_dim)
        V_s = V_s.permute(1, 0, 2, 3).reshape(num_kv_heads, n_blocks * block_size, head_dim)
        # mask the tail of the last block
        K_s = K_s[:, :ctx, :]                            # [KV_H, ctx, D]
        V_s = V_s[:, :ctx, :]
        for h in range(num_q_heads):
            kvh = h // q_heads_per_kv
            q = Q[s, h]                                  # [D]
            k = K_s[kvh]                                 # [ctx, D]
            v = V_s[kvh]
            scores = (q @ k.T) * scale                   # [ctx]
            probs = F.softmax(scores.float(), dim=-1).to(v.dtype)
            out[s, h] = probs @ v                        # [D]
    return out

The double loop is intentional: it makes the indexing obvious. Performance is irrelevant; correctness is.

Lab 02 ~120 min

First working Triton kernel, correctness-validated

Kernel writing. Difficulty: hard. Output: a Triton kernel matching the reference to within 1e-2 relative error.

Take the kernel listed in the body above. Get it compiling. Get it producing the right shape. Get it passing a correctness check against the reference. Expect at least two bugs on the way:

  • The mask boundary on the last block. Off by one will produce small numerical drift that grows with context length. Test specifically at context lengths that fill a block exactly (e.g. 256, 512) and lengths that leave 1 token in the last block (e.g. 257, 513).
  • The dtype promotion in the scores. If you compute scores in bf16 and skip the .to(tl.float32) on Q and K, you will pass tests for short contexts and fail for long ones because of accumulated rounding error.

Use this validation harness:

    K = torch.randn(total_blocks, num_kv_heads, block_size, head_dim,

Lab 03 ~90 min

Extend to multiple query tokens per sequence (prefill chunks)

Kernel extension. Difficulty: hard. Output: kernel handles both decode and prefill chunks correctly.

Real prefill has up to chunk_size query tokens per sequence per kernel launch (256 to 2048 typical). Decode has one. You want one kernel that handles both. The standard pattern is to add a third grid dimension over query tiles and to write the kernel as if each program owns a query block of size BLOCK_M (rows) attending to all of the KV blocks of the sequence (columns).

The grid becomes (num_seqs, num_q_heads, triton.cdiv(num_query_tokens_for_this_seq, BLOCK_M)). The complication is that the number of query tokens varies per sequence (some sequences are in decode with 1 query token, others are prefilling chunks of hundreds). The clean way to handle this is a flat cu_query_lens (cumulative query lengths) so a single program ID can find its sequence and its position within the sequence's queries.

You also need a causal mask now: query token i can attend to KV positions 0 .. start_pos_for_this_chunk + i. For decode, i = 0 and start_pos = ctx_len - 1, so the mask is trivially "everything." For prefill, you mask the upper triangle of the chunk's local scores.

    q_head_idx = tl.program_id(1)
    m_tile = tl.program_id(2)

    m_mask  = m_off < q_len

    ...

    acc = tl.zeros([BLOCK_M, HEAD_DIM], dtype=tl.float32)

    num_kv_blocks = (ctx_len + BLOCK_SIZE - 1) // BLOCK_SIZE

Lab 04 ~90 min

Pipeline the block loop and profile with Nsight Compute

Optimisation. Difficulty: hard. Output: 1.3x to 2x speedup over your Lab 2 kernel plus a Nsight report.

Your Lab 2 kernel is correct but probably memory-bound and not pipelining loads with compute. Two optimisations bring it within shouting distance of FA2.

First, software pipelining via tl.range(..., num_stages=2). This tells Triton to issue the load for block N+1 while computing on block N. For a memory-bound kernel like paged decode this typically yields 1.3 to 1.5x.

Second, vectorised loads. Make sure the head_dim dimension's stride is 1 (the contiguous one) and that the tl.arange over head_dim is the inner index. Triton tries to coalesce automatically but failures are common when you transpose the load by accident.

Now run Nsight Compute. The numbers to read first:

terminalcapture exactly one launch with the full set
# profile_one.sh
ncu --target-processes all \
    --launch-skip 5 --launch-count 1 \
    --set full \
    --kernel-id "::paged_attn_decode_kernel:" \
    --export profile.ncu-rep \
    python bench.py

Open profile.ncu-rep in ncu-ui and locate:

  • Compute (SM) Throughput: target above 50% for memory-bound, target above 80% for compute-bound after Lab 3 changes (tensor cores enabled).
  • Memory Throughput: for paged decode this should be 70 to 90% of peak DRAM BW; if it is below 50%, your loads are not coalescing and the inner stride is wrong.
  • Achieved Occupancy: target above 0.5; if much lower, you have register pressure (kernel uses too many registers and the SM can launch fewer warps).
  • Warp State Breakdown: under "Stall Long Scoreboard" you see how long warps wait on memory; under "Stall MIO Throttle" you see if the LSU is the bottleneck.

Diagnose what your kernel is bound on. If it is memory bound but DRAM BW is high, you are already near peak and the only path to more speed is reducing the working set (Day 4: KV quantisation). If memory bound and DRAM BW is low, you are not coalescing. If compute bound, you are using too many ops per byte loaded.

Lab 05 ~90 min

Find a regime where your kernel beats FA2 paged

Adversarial benchmarking. Difficulty: hard. Output: one regime where your kernel wins, with explanation.

FlashAttention-2 paged is heavily optimised for the common path: medium context lengths (1k to 8k), large batch sizes (16 to 128), block_size=256 internal tiling. It is excellent at this. The places it leaves performance on the table are the edges.

Three regimes worth probing:

  1. Very short contexts (under 256 tokens) with large batch. FA2's internal tile size and warp specialisation pay setup cost that does not amortise on tiny contexts. A simple Triton kernel with smaller tiles can win 1.05 to 1.2x here.
  2. Mixed sequence lengths with a heavy tail. If 90% of your batch is 256 tokens but 10% is 4096, FA2 pads to the max. Your paged kernel does not pad. The win is larger as the imbalance grows.
  3. GQA with many query heads per KV head. Your kernel can be specialised so that 4 query heads share one K block load, saving 4x on K bandwidth. FA2 has its own version of this; check whether your implementation exploits it more aggressively in some configurations.

Construct a benchmark sweep across (batch size, mean context length, context length stddev). Time both kernels (FA2 paged is in flash_attn.flash_attn_with_kvcache with block_table argument). Find one (batch, ctx, std) cell where your kernel wins by at least 5%. Explain why with Nsight evidence.

What You Should Take Away

Paging is an OS trick applied to KV. It solves fragmentation, enables prefix sharing, and pays a small constant overhead per block lookup. The block table is the data structure that makes it work; understanding it is the foundation for everything in Track A.

Online softmax is what makes long-context attention tractable. The per-block state (m, l, acc) is small and the rescaling is exact. Every modern attention kernel is some variant of this.

Triton is good enough to write production-shaped kernels, but it will lose to hand-tuned CUDA in steady state. The gap is 10 to 30 percent in most regimes. The gap closes when you exploit corner cases the production kernels do not (extreme imbalance, very small batches, specific dtype combinations).

Profiling is the work. Without Nsight, you are tuning by superstition. The four metrics (SM throughput, memory throughput, occupancy, warp state) tell you what to do next every time.

The regime map is more valuable than the speedup number. Anyone can show a kernel that wins on a chosen benchmark. The interesting question is "where does it lose, and why" because the answer reveals the limit of your kernel design.
