Responsible AI for Coding Tools: A Network-Audit Approach

May 16, 2026 ~120 min including labs 5 labs
Course Security mitmproxy Data Flow Self-Hosted

Day 1 was the lay of the land. Day 2 is where most engineers get stopped from adopting AI tools at work, and where most adoption decisions go wrong because the answer to "is this safe?" gets outsourced to the legal team's reading of a privacy policy. That is the wrong process. Privacy policies are written by lawyers for plausible deniability; the actual behaviour of a tool is determined by what crosses the wire, and you can observe that yourself in about an hour.

Today you will build a TLS-decrypting proxy, route VS Code through it, and watch in detail what each AI coding tool sends to its backend. By the end of the day you will have a per-tool data-flow diagram precise enough to satisfy a security review, evidence to back up (or contradict) the vendor's privacy claims, and a self-hosted alternative running with verified zero egress. This is the engineering version of "responsible AI." The ethics-board version is fine; this one is what actually unblocks adoption.

Legal note before you start: route only your own code, on a machine you own, through your proxy. Do not capture traffic from other people's sessions or from corporate networks without authorisation. The point of this lab is to make informed decisions about tools you use; it is not to reverse-engineer vendor protocols or extract proprietary information.

The Threat Model, Made Concrete

When a security team asks "is Copilot safe?", they usually mean some combination of five questions, all of which have different answers and different evidence requirements:

  1. Where does my code go? Which servers receive what, on which endpoints, under whose jurisdiction.
  2. How long is it kept? Retention windows for prompts, completions, and feedback, and whether retention applies to enterprise tiers.
  3. Who has access to it? Vendor staff, model trainers, downstream subprocessors, government requests.
  4. Could it train future models? The "no training on your data" claim is only as strong as the audit trail behind it.
  5. Could it leak into someone else's output? The infamous "Copilot suggested someone else's GPL code" failure mode, which is a matter of public-code matching and licence detection, not training.

The privacy policies of every major vendor address all five questions. They do so in language that is technically true and operationally ambiguous. The way you get past the ambiguity is to measure the behaviour: capture the actual traffic, examine the request bodies, and reconcile what you see with what the vendor claims. When the two match, your security team has evidence. When they do not, you have a question to ask in writing before adoption.

Why mitmproxy Is the Right Primitive

The tool you want for this is mitmproxy. It is an open-source HTTPS proxy that installs its own certificate authority into your trust store, intercepts TLS connections originating from your machine, decrypts them, lets you inspect and modify them, then re-encrypts and forwards to the real backend. Other tools work (Burp Suite, Charles Proxy, Wireshark with SSLKEYLOGFILE), but mitmproxy has the best CLI, the cleanest Python API for scripting analyses, and a permissive licence.

The key thing to understand is that you are interposing yourself between your own machine and the vendor backend. Your VS Code, your OS, your CA store. You are not breaking anyone's TLS; you are installing your own root certificate that you control and trust on a machine you own.

Setup, before the first lab

Install once, use for all five labs.

terminalinstall mitmproxy
# macOS
brew install mitmproxy

# Linux (Debian/Ubuntu)
sudo apt install mitmproxy

# Or via pipx, which works everywhere
pipx install mitmproxy

# Start it once to generate the CA cert at ~/.mitmproxy/
mitmproxy
# (press q to quit)
ls ~/.mitmproxy/
# mitmproxy-ca-cert.pem   mitmproxy-ca.p12   mitmproxy-ca.pem   ...

Now trust the CA so HTTPS interception works. The exact command differs by OS.

terminaltrust the CA (macOS)
# macOS: import into the system keychain
sudo security add-trusted-cert -d -p ssl -p basic \
  -k /Library/Keychains/System.keychain \
  ~/.mitmproxy/mitmproxy-ca-cert.pem

# Verify it landed
security find-certificate -c mitmproxy /Library/Keychains/System.keychain
terminaltrust the CA (Linux)
# Linux (Debian/Ubuntu): copy to the system CA bundle
sudo cp ~/.mitmproxy/mitmproxy-ca-cert.pem \
        /usr/local/share/ca-certificates/mitmproxy.crt
sudo update-ca-certificates

# Verify
awk -v cmd='openssl x509 -noout -subject' '/BEGIN/{close(cmd)};{print | cmd}' \
  /etc/ssl/certs/ca-certificates.crt | grep -i mitmproxy

You also need Node.js to trust it, because VS Code's extensions make their own HTTPS calls through Node and Node has its own CA bundle.

terminalpoint Node and VS Code at the CA
# Make Node trust the CA bundle on every invocation
export NODE_EXTRA_CA_CERTS="$HOME/.mitmproxy/mitmproxy-ca-cert.pem"
# Persist this in your shell rc so VS Code's terminal inherits it.

# Launch VS Code with the proxy set
export HTTPS_PROXY="http://127.0.0.1:8080"
export HTTP_PROXY="http://127.0.0.1:8080"
code .

# In another terminal, start mitmweb (web UI on :8081)
mitmweb --listen-port 8080

At this point you have a proxy listening on 8080, a UI on 8081, and VS Code routed through it. Open the UI in a browser, go to http://127.0.0.1:8081, and you should see HTTPS traffic flowing as you interact with VS Code. If you do not, your environment variables are not making it to VS Code; restart your terminal and the editor.

One last thing: some tools pin their certificate (Cody historically did, Copilot occasionally does for specific endpoints). If you see SSL: certificate verify failed in the tool's logs, that tool has pinning enabled and you will have to use mitmproxy's --ssl-insecure mode for capture and skip the lab's interception step for that specific connection. Note this in your audit report.

The Labs

Lab 01 ~25 min

Capture and dissect a single tab-completion request

Tools: any inline-completion tool of your choice. Difficulty: medium.

You will trigger one ghost-text completion and read exactly what the tool sends. This is the foundation lab; every subsequent one builds on it.

Procedure

  1. With mitmproxy running and VS Code routed through it, open an empty .py file in your test repo.
  2. In the mitmweb UI, click the broom icon to clear current flows.
  3. Type def fibonacci(n: int) -> int: and press Enter. Wait for the ghost text to appear.
  4. Press Escape to dismiss it (do not accept; we just want the request).
  5. In mitmweb, find the request to the tool's completion endpoint. Common patterns: api.githubcopilot.com/copilot_internal/v2/engines/copilot-codex/completions for Copilot, api2.cursor.sh or repo42.cursor.sh for Cursor, codeium.com for Codeium.
  6. Click the request. Switch to the "Request" pane. Read the headers and body in full.

What to look for

  • The endpoint URL and HTTP method. Note the path; this is where your code is going.
  • Authentication header. Bearer token? Custom header? Note its shape, never the value.
  • Body format. JSON? Protobuf? gRPC over HTTP/2? The format determines how easy it is to audit.
  • Prefix and suffix fields. How much of your file did it send? Just the current line? The whole file? Surrounding files?
  • Repository/file metadata. Did it send a file path? Branch name? Git remote URL?
  • Headers identifying the user, machine, or organisation. Telemetry ID? Session ID? Editor version?
expected (Copilot, redacted)shape of one completion request
POST https://api.githubcopilot.com/copilot_internal/v2/engines/.../completions
Headers:
  Authorization: Bearer ghu_REDACTED
  Editor-Version: vscode/1.94.0
  Editor-Plugin-Version: copilot/1.245.0
  Openai-Organization: github-copilot
  VScode-MachineId: REDACTED
  VScode-SessionId: REDACTED/REDACTED

Body (JSON):
{
  "prompt": "# Path: scratch.py\ndef fibonacci(n: int) -> int:\n",
  "suffix": "",
  "max_tokens": 500,
  "temperature": 0,
  "top_p": 1,
  "n": 1,
  "stop": ["\n\n\n"],
  "nwo": "your-github-username/your-repo",
  "stream": true,
  "extra": { "language": "python", "next_indent": 4 ... }
}

Note specifically the nwo field. That stands for "name-with-owner" and identifies the repository. If your file is inside a private repo you did not realise the tool would identify, this is the data point that proves it does.

Deliverable

A single-page markdown note per tool, listing: endpoint URL, body schema (with field-by-field annotation), any identifiers transmitted, and one specific surprise (there will be at least one). Keep this; you will reuse it on Day 4.

Lab 02 ~25 min

Build a per-tool data-flow diagram

Difficulty: medium. Output: a diagram you can defend to a CISO.

Repeat Lab 01 for three tools, then merge the findings into one diagram per tool. The diagram should answer: when I press Tab once, what data goes where, in what order, under what protocol?

A useful template (Mermaid format because it lives in a markdown file alongside the rest of your audit):

Fill in the body size (a real number from your capture), the protocol (HTTP/2? HTTP/1.1?), and the response style (SSE stream? single JSON?). Then mark every node with the jurisdiction of the company that operates it. This is the bit that surprises people most often. The frontend API may be operated by one company, the model itself by another, and the telemetry by a third. For audit purposes, all three matter.

Repeat for chat completions (the request body will be much larger; chat tools typically send the current file plus retrieved chunks). Repeat for agent operations if your tool supports them; this is where the volume of egress jumps by an order of magnitude.

Deliverable

Three Mermaid diagrams (one per tool) in a single markdown file, each with annotated edges (body sizes, frequencies, protocols) and node jurisdictions. This file is the artefact that gets you past security review. Update it whenever a vendor changes its architecture.

Lab 03 ~30 min

Probe the public-code-matching defence

Difficulty: medium-hard. Tests vendor claims with adversarial input.

Most major vendors claim a "public code filter" that prevents the model from regurgitating verbatim copies of indexed public code. The claim is reasonable; the question is whether it actually works under realistic conditions. You will test it directly.

Setup

Pick a function from a well-known open-source repository. Something distinctive but not in the model's likely training corpus enough to be memorised by name. A good target: a non-trivial helper from a mid-popularity GitHub project, twenty to fifty lines, with at least one comment block that is verbatim a unique phrase.

Procedure

  1. Open an empty file. Paste the function, then delete its body, leaving the signature and the leading comment.
  2. Position your cursor at the end of the signature. Wait for ghost text.
  3. Capture the request (Lab 01 procedure) and the response.
  4. Compare the suggestion to the original. Specifically: how many tokens match exactly? Does the unique comment phrase appear? Does the suggestion include the original's quirks (variable names, edge-case handling)?
  5. If the suggestion is the same code, the public-code filter did not fire on this input. If the suggestion is similar but altered (different variable names, restructured logic), the filter fired but was applied as a "rewrite" rather than a block.
  6. Repeat with the filter explicitly enabled or disabled where the setting is exposed (Copilot has it in user settings; document its default).

What you are measuring

  • Verbatim match rate: the fraction of suggestion tokens that exactly match the original. Above 30% on a 50-token suggestion is a real signal.
  • Filter behaviour: does the tool block, rewrite, or pass through?
  • Latency penalty: turning on the filter often adds 100 to 300ms; measure it.
  • License signal: some tools, post-suggestion, return a list of repositories the suggestion resembled. Does yours?

One important caveat: this lab tests recall under prompting, not memorisation in the abstract. A tool that does not fire on your specific function may fire on others, and a tool that does fire may not catch a rephrased version. The point is not to prove the filter is broken; it is to characterise its behaviour precisely enough that your team knows what protection they actually have.

Deliverable

A markdown table with one row per tool, columns for (verbatim-match-rate, filter-behaviour, latency-penalty-ms, license-attribution-y/n) and a short note on three test inputs. Conclusion line: "for inputs of this shape, on this tool, the public-code filter behaves as follows."

Lab 04 ~25 min

Set up a self-hosted alternative with verified zero egress

Difficulty: medium. Tools: Continue + ollama. Output: a working stack that egresses nothing.

The cloud tools are convenient but they are not the only option. A self-hosted stack runs the model on your machine and never makes a network call. This lab proves that with the same audit machinery you built in Lab 1.

Procedure

terminalinstall ollama and a code model
# macOS / Linux
curl -fsSL https://ollama.com/install.sh | sh

# Pull a code-tuned model. deepseek-coder-v2 is a good default; the
# 6.7B variant runs on 16GB of system RAM, 16B needs a GPU.
ollama pull deepseek-coder-v2:6.7b

# Verify it serves locally
curl http://localhost:11434/api/generate -d '{
  "model": "deepseek-coder-v2:6.7b",
  "prompt": "def fibonacci(n: int) -> int:",
  "stream": false
}' | head -c 300
terminalinstall Continue and point it at ollama
# Install the Continue VS Code extension from the marketplace.
# Then edit ~/.continue/config.json to use ollama:
cat > ~/.continue/config.json <<'JSON'
{
  "models": [{
    "title": "DeepSeek Coder local",
    "provider": "ollama",
    "model": "deepseek-coder-v2:6.7b",
    "apiBase": "http://localhost:11434"
  }],
  "tabAutocompleteModel": {
    "title": "Tab autocomplete (local)",
    "provider": "ollama",
    "model": "deepseek-coder-v2:6.7b",
    "apiBase": "http://localhost:11434"
  },
  "allowAnonymousTelemetry": false,
  "telemetry": false
}
JSON

Verify zero egress

This is the auditable claim. With mitmproxy running on 8080 and VS Code routed through it, clear the flows in mitmweb. Then use Continue: trigger a completion, run a chat query, ask it to refactor something. After five minutes of active use, look at the mitmweb flows list.

What you should see: HTTP requests to localhost:11434 (your ollama server) and nothing else from the Continue extension. No continue.dev. No telemetry endpoints. No model providers. If you do see external traffic, the telemetry flag is being ignored or a different extension is responsible; track it down before declaring the stack airgapped.

For an even stronger guarantee, run this in a network namespace or container with the loopback interface only. The tightest setup uses unshare -n on Linux to launch a shell with no network access except loopback; ollama and VS Code happily run inside it.

terminalnuclear option: no network at all
# Linux only. Drops you into a shell with loopback as the only interface.
sudo unshare -n bash -c '
  ip link set lo up
  echo "Interfaces in this namespace:"
  ip addr show
  echo
  echo "Try to reach anything outside loopback (should fail):"
  curl --max-time 3 https://api.github.com || echo "blocked, as expected"
'
Deliverable

A short audit memo: "I ran X minutes of active Continue+ollama use through a TLS-decrypting proxy. The only flows captured were to localhost:11434. Conclusion: this stack has zero external egress for code content under tested workloads." Attach a screenshot of the mitmweb flow list. This is the artefact you give to security to prove the claim.

The Failure Modes I See Most Often

Two failure modes show up over and over in real audits, both worth flagging before they catch you out.

Telemetry that is not in the privacy policy. The completion request body is not the only thing tools send. There is almost always a separate telemetry endpoint that fires on extension activation, on every keystroke (debounced), and on every accept/reject. The data in those calls is summarised, not raw code, but it still tells the vendor what languages you use, what frameworks you import, how often you reject suggestions, and on which file paths. The privacy policy may or may not address it. Lab 1 surfaces it; do not stop at the completion endpoint.

The "enterprise tier" assumption. Vendors often have stronger privacy guarantees on their enterprise SKUs. The trap is assuming that paying for enterprise applies the guarantees automatically. It does not, usually. There is a per-organisation setting that enables the no-training, no-retention behaviour, and it may default to off. Run Lab 1 against the actual SKU your organisation pays for; do not assume.

Two failure modes I see on the other side of the table:

Security teams that reject without measurement. "No AI tools, ever" is not a security posture; it is an unwillingness to do the audit work that would allow informed adoption. Push back, kindly, with the artefact from Lab 5. The conversation shifts when there is evidence on the table.

Engineering teams that adopt without measurement. The mirror image. "Everyone uses Copilot so we should too" is not a posture either. The same memo applies; fill it in honestly and you will discover settings you need to flip, tools you should not adopt yet, and a self-hosted fallback for the cases where the cloud is wrong.

What You Should Take Away

Behaviour beats policy. A vendor's privacy policy is the starting point of an audit, not the conclusion. The actual data flow is observable and auditable; do the work.

Telemetry is the part nobody talks about. Code content matters most, but the metadata stream (file types, languages, accept rates, machine IDs) is non-trivial and tells the vendor more than people realise.

Self-hosting is a real fallback. Continue plus ollama with a 6.7B model is not as polished as Copilot, but it is correct, free, and provably airgapped. For some teams and some codebases, that is the right answer regardless of how good the cloud tools get.

The artefact is the unlock. A one-page evidence-based memo is the difference between "we are not sure" and "we have decided." It is also the difference between a tool adoption that lasts and one that gets pulled in three months when a security incident makes everyone re-litigate the decision.
