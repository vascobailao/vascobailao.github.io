How Code Completion Actually Works: Building an FIM Engine from Scratch

May 17, 2026 ~150 min including labs 5 labs
Course FIM llama.cpp Tokenisation Latency VS Code

On Day 1 you measured inline-completion latency as a black box. Today you open the box. By the end of this lesson you will have built a working fill-in-the-middle completion server, written a VS Code extension that talks to it, instrumented the entire latency stack from keystroke to rendered ghost text, and you will understand precisely why Copilot and Cursor's tab model behave the way they do. This is the most code-heavy day in the course. It is also the one that changes how you think about every completion tool you will ever use, because once you have built the thing, the marketing claims become legible.

The central insight you should hold onto: code completion is not "the model writes code." It is a specific, constrained inference problem called fill-in-the-middle, run under a latency budget so tight that most of the engineering is about not calling the model, or calling it as little as possible. The model is the easy part. The plumbing around it (tokenisation, debouncing, cancellation, caching, streaming, rendering) is where completion tools win or lose.

What "Fill in the Middle" Actually Means

A base language model is trained to predict the next token given everything before it. That is left-to-right, or "causal," generation. It is exactly the wrong shape for code completion, because when you are editing code your cursor is almost never at the end of the file. You are in the middle of a function, with code before the cursor (the prefix) and code after it (the suffix). A pure left-to-right model cannot see the suffix, so it does not know that three lines below your cursor there is a return result that constrains what you are about to write.

Fill-in-the-middle (FIM) is a training and inference trick that teaches a causal model to fill a gap. During training, documents are split into three pieces (prefix, middle, suffix) and reordered so the model learns to generate the middle given the prefix and suffix. The technique was popularised by the 2022 OpenAI paper "Efficient Training of Language Models to Fill in the Middle," and essentially every code-completion model since (StarCoder, CodeLlama, DeepSeek-Coder, Qwen-Coder) ships FIM-capable weights.

The reordering uses sentinel tokens. The most common scheme is "PSM" (prefix, suffix, middle):

conceptFIM PSM framing
Your file, with cursor at |:

    def add(a, b):
        |
        return result

Becomes this single token sequence fed to the model:

    <fim_prefix>def add(a, b):\n    <fim_suffix>\n    return result<fim_middle>

The model generates from after <fim_middle>. It has seen both the
prefix AND the suffix, so it knows a `result` variable must exist
and will write something like:  result = a + b

The sentinel tokens differ by model family, and getting them wrong is the single most common reason a home-grown completion setup produces garbage. This is important enough that one of today's labs is entirely about token formats.

Note DeepSeek's tokens use full-width unicode bars and a special "hole" naming. Copy them exactly from the model's tokenizer config; typing them by hand will fail silently because the bytes will not match the trained sentinels, and the model will treat them as ordinary text.

The Latency Stack

When you press a key and ghost text appears, here is everything that happened, in order, with the rough time budget each stage gets if the total is to stay under the 200ms that feels instant:

  1. Keystroke to trigger decision (0ms): the editor decides whether this keystroke should trigger a completion at all. Typing inside a string literal? Probably not. Just typed a .? Probably yes.
  2. Debounce (50 to 150ms): the editor waits to see if you keep typing. If you do, the in-flight request is cancelled. This is the single most important latency-management technique and the one people forget.
  3. Context assembly (1 to 10ms): gather the prefix, the suffix, and optionally snippets from other open files.
  4. Tokenisation (1 to 5ms): convert the FIM-framed string to token IDs.
  5. Network round trip (10 to 60ms): for cloud tools. Zero for local.
  6. Prefill (10 to 80ms): the model processes the entire prompt in one forward pass to build the KV cache. This scales with prompt length.
  7. Decode to first token (10 to 40ms): the first generated token. Time-to-first-token (TTFT) is what the user perceives as "did it respond."
  8. Decode remaining tokens (streamed): the rest of the suggestion, streamed and rendered progressively.
  9. Render (1 to 5ms): draw the ghost text, handling partial tokens and multi-line suggestions.

The thing to notice is that the model inference (prefill plus decode) is maybe half the budget, and the other half is editor-side engineering. A tool with a great model and bad debouncing feels worse than a tool with a mediocre model and great debouncing. This is why "which model does it use" is the wrong first question about a completion tool.

Prerequisites for today: a machine that can run llama.cpp (any laptop with 16GB RAM works for a 1.3B model), Node.js 20+, Python 3.11+, and VS Code. You will download about 1GB of model weights. Budget the full setup time; the labs build on each other in sequence.

Now the critical part: call it with DeepSeek's exact FIM tokens. We use the raw /completion endpoint, not the chat endpoint, because we are doing FIM, not conversation.

fim_call.pyone correct FIM completion
import requests

# DeepSeek-Coder FIM sentinels. Copy these bytes exactly.
PREFIX = "<｜fim▁begin｜>"
HOLE   = "<｜fim▁hole｜>"
END    = "<｜fim▁end｜>"

def fim_complete(prefix: str, suffix: str, n_predict: int = 64) -> str:
    prompt = f"{PREFIX}{prefix}{HOLE}{suffix}{END}"
    r = requests.post("http://localhost:8080/completion", json={
        "prompt": prompt,
        "n_predict": n_predict,
        "temperature": 0.2,
        "top_p": 0.9,
        # stop as soon as the model tries to continue past the hole
        "stop": ["<｜fim▁begin｜>", "<｜fim▁end｜>", "\n\n"],
        "stream": False,
    })
    return r.json()["content"]

prefix = "def add(a, b):\n    "
suffix = "\n    return result"
print(repr(fim_complete(prefix, suffix)))

Now run the experiment that teaches the lesson: call it again with the wrong tokens (use Qwen's <|fim_prefix|> with this DeepSeek model). You will get nonsense, because the model never saw those byte sequences as sentinels during training and treats them as literal text. This failure is silent, which is exactly why it bites people.

Lab 02 ~35 min

Write a 60-line VS Code extension that requests completions

Difficulty: medium-hard. Output: ghost text in a real editor, served by your model.

This is the lab that makes it real. VS Code exposes an InlineCompletionItemProvider API. You will implement it, point it at your llama.cpp server, and get ghost text from a model running on your own machine.

extension.tsminimal inline completion provider
import * as vscode from "vscode";

const PREFIX = "<｜fim▁begin｜>";
const HOLE   = "<｜fim▁hole｜>";
const END    = "<｜fim▁end｜>";

async function fim(prefix: string, suffix: string,
                   signal: AbortSignal): Promise<string> {
  const res = await fetch("http://localhost:8080/completion", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      prompt: `${PREFIX}${prefix}${HOLE}${suffix}${END}`,
      n_predict: 64, temperature: 0.2,
      stop: [PREFIX, END, "\n\n"], stream: false,
    }),
    signal,
  });
  const data = await res.json() as { content: string };
  return data.content;
}

export function activate(ctx: vscode.ExtensionContext) {
  const provider: vscode.InlineCompletionItemProvider = {
    async provideInlineCompletionItems(doc, pos, _ctx, token) {
      // Build prefix and suffix around the cursor.
      const fullText = doc.getText();
      const offset = doc.offsetAt(pos);
      const prefix = fullText.slice(0, offset);
      const suffix = fullText.slice(offset);

      // Wire VS Code's cancellation token to fetch's AbortController.
      const ac = new AbortController();
      token.onCancellationRequested(() => ac.abort());

      try {
        const completion = await fim(prefix.slice(-2000),
                                     suffix.slice(0, 1000), ac.signal);
        if (!completion.trim()) return { items: [] };
        return { items: [{ insertText: completion, range:
          new vscode.Range(pos, pos) }] };
      } catch {
        return { items: [] };   // aborted or errored: show nothing
      }
    },
  };
  ctx.subscriptions.push(
    vscode.languages.registerInlineCompletionItemProvider(
      { pattern: "**" }, provider));
}

Scaffold this with yo code (the official extension generator), drop in the provider, run the Extension Development Host (F5), and open a Python file. Type a function signature and you should see ghost text from your local model. If you see nothing, check three things in order: is llama.cpp serving on 8080, are the FIM tokens correct, and is the provider registered for the file's language.

Note the two details that matter for quality: we slice the prefix to the last 2000 characters and the suffix to the first 1000. Sending the entire file would blow the latency budget on prefill. This window choice is exactly the kind of decision every completion tool makes, and it is why completions degrade in very large files.

Deliverable

A running extension that produces ghost text from your local model. Record one screenshot and a note on the prefix/suffix window sizes you chose and why. You have now built the core of Copilot.

Lab 03 ~25 min

Add debouncing and cancellation, then measure keystroke-to-ghost-text

Difficulty: medium. The lab that teaches why latency engineering beats model choice.

The naive extension from Lab 2 fires a request on every keystroke. That is wasteful and slow: you start a 64-token generation, then the user types another character and you throw it away. Add a debounce so you only fire after the user pauses, and make sure the cancellation actually aborts in-flight work.

debounce.ts150ms debounce with proper cancellation
let pending: NodeJS.Timeout | undefined;
let inflight: AbortController | undefined;

function debouncedFim(prefix: string, suffix: string,
                      delayMs = 150): Promise<string> {
  // cancel a queued request and any in-flight network call
  if (pending) clearTimeout(pending);
  if (inflight) inflight.abort();

  return new Promise((resolve) => {
    pending = setTimeout(async () => {
      inflight = new AbortController();
      const t0 = performance.now();
      try {
        const out = await fim(prefix, suffix, inflight.signal);
        const ms = performance.now() - t0;
        console.log(`[fim] ${ms.toFixed(0)}ms  ${out.length} chars`);
        resolve(out);
      } catch {
        resolve("");        // aborted: yield nothing
      }
    }, delayMs);
  });
}

Now instrument it. Log the time from the provider being invoked to the suggestion being returned. Type a 200-character function at a natural speed and read the console. You will see most keystrokes produce no model call at all, because the debounce cancelled them. The calls that do fire are the ones where you paused, which is exactly when you want a suggestion.

Run a controlled measurement: type the same five prompts from Day 1's Lab 3, three times each, and record the median keystroke-to-ghost-text time for your local setup. Compare it to the numbers you recorded for Copilot and Cursor on Day 1. A 1.3B model on a laptop CPU is often in the same latency band as a cloud tool, because what you save on network you spend on slower local compute, and vice versa.

Lab 04 ~25 min

FIM vs. raw next-token completion on the same prefix

Difficulty: medium. Proves why suffix-awareness matters.

This lab isolates the value of FIM. You will complete the same gap two ways: with proper FIM framing (the model sees the suffix), and with naive left-to-right completion (prefix only, suffix discarded). The difference is stark on any code where the suffix constrains the answer.

fim_vs_causal.pycontrolled comparison
import requests

def call(prompt, stop):
    return requests.post("http://localhost:8080/completion", json={
        "prompt": prompt, "n_predict": 48, "temperature": 0.0,
        "stop": stop, "stream": False,
    }).json()["content"]

PREFIX, HOLE, END = "<｜fim▁begin｜>", "<｜fim▁hole｜>", "<｜fim▁end｜>"

# A gap where the SUFFIX determines the right answer.
prefix = "def totals(items):\n    total = 0\n    for x in items:\n        "
suffix = "\n    return total"

fim_out    = call(f"{PREFIX}{prefix}{HOLE}{suffix}{END}", [PREFIX, END, "\n\n"])
causal_out = call(prefix, ["\n\n", "def "])   # no suffix knowledge

print("FIM    :", repr(fim_out))
print("CAUSAL :", repr(causal_out))
outputsuffix-awareness in action
FIM    : 'total += x'          # knows `total` is returned below
CAUSAL : 'print(x)'            # plausible, but breaks the return

Construct five such examples where the suffix matters: a variable defined after the cursor, a closing bracket that constrains structure, a return type annotation that determines the value, a loop that expects accumulation, a context manager that must be closed. For each, run both modes and score whether the completion is consistent with the suffix. FIM should win most of them; document the cases where it does not, because those reveal the model's limits.

Lab 05 ~30 min · capstone for Day 3

Profile prefill vs. decode and reason about completion-tool architecture

Difficulty: hard. Output: the numbers that explain every completion product decision.

The final lab connects the inference internals to product behaviour. You will measure how prefill time scales with prompt length and how decode time scales with output length, then use those numbers to explain why completion tools make the design choices they make.

llama.cpp's server returns timing data in its response. Extract it and sweep the prompt length.

profile.pyprefill/decode timing sweep
import requests, statistics

PREFIX, HOLE, END = "<｜fim▁begin｜>", "<｜fim▁hole｜>", "<｜fim▁end｜>"
filler = "    x = compute_something(a, b, c)  # padding line\n"

def timed(prefix_lines: int, n_predict: int):
    prefix = "def f():\n" + filler * prefix_lines + "    "
    suffix = "\n    return x"
    r = requests.post("http://localhost:8080/completion", json={
        "prompt": f"{PREFIX}{prefix}{HOLE}{suffix}{END}",
        "n_predict": n_predict, "temperature": 0.0,
        "stop": [END], "stream": False,
    }).json()
    t = r["timings"]
    return {
        "prompt_tokens": t["prompt_n"],
        "prefill_ms": t["prompt_ms"],
        "decode_ms": t["predicted_ms"],
        "decoded_tokens": t["predicted_n"],
        "ms_per_decode_token": t["predicted_ms"] / max(t["predicted_n"], 1),
    }

print(f"{'ctx_lines':>9} {'prompt_tok':>10} {'prefill_ms':>10} "

Read these numbers carefully because they explain every product decision in the completion space:

  • Prefill scales roughly linearly with prompt length. Going from 28 to 2412 prompt tokens took prefill from 41ms to 643ms. This is why tools window the context: sending your whole 5000-line file would put prefill alone over a second, blowing the budget. The prefix/suffix slicing from Lab 2 is not laziness, it is a hard latency requirement.
  • Decode time per token is roughly constant (here 2.8ms/token) and independent of context length once the KV cache is built. This is why completions are kept short: a 64-token suggestion costs about 180ms of decode regardless of context, and longer suggestions are rarely accepted anyway.
  • Time-to-first-token is dominated by prefill on long contexts. This is why prefix caching (reusing the KV cache for an unchanged prefix across keystrokes) is the highest-leverage optimisation a completion tool can make, and why the good ones do it.

Now do the reasoning exercise. Given these curves, explain in writing: (a) why Cursor built a custom small model for tab completion rather than using a big general model, (b) why completion quality degrades in very large files, (c) why a tool might cap suggestions at one line by default and only expand on demand, and (d) why prefix caching matters more than a faster GPU for this workload. Each answer should reference a specific number from your sweep.

The Failure Modes I See Most Often

Wrong FIM tokens, failing silently. Covered in Lab 1 but worth repeating because it is the number one cause of "I tried to build a completion tool and it produced garbage." The sentinel tokens are model-specific byte sequences. Copy them from the tokenizer config, never type them by hand, and verify with a known-good example before building anything on top.

Sending too much context. The instinct is "more context equals better completion." The latency sweep shows why that is wrong: prefill cost grows with context, and past a point the marginal context does not improve the suggestion enough to justify the latency. Good completion tools send a carefully chosen window, not the whole repo.

No cancellation. If your in-flight requests do not actually abort when the user keeps typing, you pay for generation you throw away, your server saturates, and latency climbs under load. The AbortController wiring in Lab 2 and 3 is not optional polish; it is load-bearing.

Using an instruct model for raw FIM. Instruct-tuned models are optimised for chat turns and tend to add explanations, markdown fences, or refuse to "just complete." For inline completion you want the base model with FIM weights. This surprises people who assume the chat-tuned model is strictly better.

What You Should Take Away

Completion is FIM, not chat. The model is filling a gap with full knowledge of what comes after the cursor. This is a different inference shape from the one most people picture, and it is why suffix-awareness matters.

The plumbing is the product. Tokenisation, windowing, debouncing, cancellation, prefix caching, and streaming are where completion tools differentiate. The model is necessary but not sufficient, and often not even the bottleneck.

Latency is a budget, and you can see the line items. You now have measured numbers for prefill, decode, and round trip. When a vendor claims a latency improvement, you can reason about which line item they optimised and whether it matters for your file sizes.

A worse model with better latency wins inline. This is the single most counterintuitive takeaway, and you proved it: a 1.3B local model with tight debouncing can feel better than a larger cloud model with sloppy request management. Latency dominates perceived quality in the inline mode.
