Agent Engineering

How Coding Agents Actually React to Terminal Output

May 11, 2026 22 min read Hands-on
Agents Tool Use PTY Bash Reactive Control

The thing that distinguishes a real coding agent from a glorified prompt-completer is what it does with terminal output. Anyone can wire an LLM to a subprocess.run call and feed the result back into the prompt. That works for the first ten commands and then quietly falls apart, because the terminal is a much weirder I/O surface than people remember, and "feed the output back" is doing more work in that sentence than it can carry. The interesting engineering is in how the agent reacts: when to stream, when to truncate, when to re-prompt, when to give up, when to ask, when to silently retry.

This post is a teardown of that reactive layer, drawn from building it (and watching it break) inside a couple of agent products and from spending too much time staring at why a perfectly capable model would loop forever on a command that any human would have killed in two seconds. The right mental model is not "tool use." It is closed-loop control. The agent is a controller, the terminal is the plant, and the output is the feedback signal. Most of the failure modes are what you would expect from a controller with a noisy, partially observable, latency-jittered sensor.

The Naive Pattern, and Why It Stops Working

The starting point for almost every agent that has ever shipped is some version of this:

naive_bash.pythe pattern that breaks
def bash(cmd: str, timeout: int = 60) -> dict:
    p = subprocess.run(
        ["bash", "-lc", cmd],
        capture_output=True, text=True, timeout=timeout,
    )
    return {
        "stdout": p.stdout,
        "stderr": p.stderr,
        "exit_code": p.returncode,
    }

This is fine for ls, cat README.md, and echo hello. It breaks the moment the agent runs anything real. Five things go wrong, in escalating severity.

The output is huge. A test suite, a build log, an npm install, a terraform plan, anything that touches a real codebase produces tens of thousands of lines. Dumping that into the model's context wastes tokens, evicts more useful information, and routinely pushes the model past the point where it can reason coherently. The agent ends up "summarising" output it has not actually understood.

The output is full of escape codes. Most CLIs detect a TTY and emit ANSI colour sequences, cursor-movement codes, and progress-bar carriage returns when one is attached. Pipe their output to capture_output and many of them switch off colours, but a stubborn fraction (Cargo, ESLint with certain configs, anything wrapping indicatif, recent versions of npm with --color=always in CI configs) emit the codes anyway. The model sees \x1b[1;32m✓\x1b[0m instead of a checkmark, and worse, it sees a screen of \r\x1b[K sequences from a progress bar that visually rendered as one updating line but textually expanded into a thousand.

The command hangs on an interactive prompt. sudo wants a password. git push wants a passphrase. npm init wants you to confirm fifteen defaults. Without a TTY, some of these silently wait forever; others fail with errors that do not say "I needed input." The naive wrapper either times out (losing all the work the command did before the prompt) or hangs the agent loop entirely.

The command finishes but the exit code lies. grep returns 1 when it finds nothing, which is not a failure. diff returns 1 when files differ, which is the answer. make returns 0 even when the underlying compiler emitted warnings the user wanted treated as errors. Treating exit-code-zero as success and non-zero as failure is the agent's default and it is wrong often enough to matter.

The command is long-running and the agent is blocked. Running pytest on a real test suite, docker build, cargo build --release, anything that takes a minute, blocks the main agent loop. The model cannot do anything else, including answering "are you still working on this?" Worse, if the user wants to redirect or cancel, there is no surface to do it on.

Each of these is independently survivable. The problem is that they compound. A real coding agent runs a hundred commands per session and any individual one of them can hit any of these failure modes. The reactive layer exists to handle them at the system level rather than asking the model to reason about them every single time.

The Right Architecture, in Five Pieces

What follows is the architecture I have converged on across several agent builds. None of the individual pieces are clever. The combination is what gives the model a sensor it can actually trust.

1. Streaming execution with line-buffered capture

Replace subprocess.run with a streaming reader that emits lines as they appear. This unblocks two things at once: the agent can react to early output without waiting for completion, and you can attach a watcher that detects the failure modes above as they happen rather than after the fact.

streamer.pyline-buffered execution with watchers
import asyncio, signal, time
from collections import deque

async def stream_bash(cmd: str, *, timeout=600, max_lines=4000,
                      watchers=()):
    proc = await asyncio.create_subprocess_exec(
        "bash", "-lc", cmd,
        stdout=asyncio.subprocess.PIPE,
        stderr=asyncio.subprocess.STDOUT,   # interleave preserves ordering
        env={**os.environ, "TERM": "dumb",  # discourage ANSI codes
             "NO_COLOR": "1", "CI": "1",
             "PAGER": "cat", "GIT_PAGER": "cat",
             "DEBIAN_FRONTEND": "noninteractive"},
    )
    head, tail = [], deque(maxlen=200)
    n_lines = 0
    started = time.monotonic()
    early_exit = None

    async for raw in proc.stdout:
        line = raw.decode("utf-8", "replace").rstrip("\n")
        n_lines += 1
        (head if n_lines <= 200 else tail).append(line)

        for w in watchers:
            verdict = w(line)
            if verdict == "kill":
                proc.send_signal(signal.SIGTERM)
                early_exit = w.reason
                break

        if time.monotonic() - started > timeout:
            proc.send_signal(signal.SIGTERM); early_exit = "timeout"; break

    code = await proc.wait()
    return {
        "exit_code": code,
        "head": head,
        "tail": list(tail),
        "n_lines": n_lines,
        "early_exit": early_exit,
        "elapsed": time.monotonic() - started,
    }

Three details in that snippet pull more weight than they look. First, TERM=dumb plus NO_COLOR=1 plus CI=1 is the ritual incantation that disables colours and progress bars in roughly 95% of modern CLIs. The remaining 5% need a postprocessor (next section). Second, stderr=STDOUT interleaves the streams in their natural temporal order. The alternative, capturing them separately and reconstructing the order, is impossible in general because the OS does not promise it. Third, head + tail is the right summarisation primitive: keep the first 200 lines (where the command's intent and configuration live) and the last 200 (where errors and results live). Discarding the middle is almost always correct.

2. PTY allocation when the command needs it

For commands that misbehave when stdout is a pipe (some test runners, some build tools, any program that calls isatty and then refuses to do its job), you need an actual pseudo-terminal. The agent should pick: pipe by default, PTY when the command is on a known list or when a first-attempt pipe execution returned a tell-tale "stdout is not a tty" error.

pty_runner.pyfallback to PTY
import pty, os, select, errno

def run_with_pty(cmd, timeout=600):
    pid, fd = pty.fork()
    if pid == 0:
        os.execvp("bash", ["bash", "-lc", cmd])

    output = bytearray()
    deadline = time.monotonic() + timeout
    while True:
        remaining = deadline - time.monotonic()
        if remaining <= 0:
            os.kill(pid, signal.SIGTERM); break
        r, _, _ = select.select([fd], [], [], min(remaining, 0.5))
        if not r:
            continue
        try:
            chunk = os.read(fd, 65536)
        except OSError as e:
            if e.errno == errno.EIO: break    # child closed PTY
            raise
        if not chunk: break
        output.extend(chunk)
        # detect interactive prompt patterns and abort early
        if INTERACTIVE_PROMPT_RE.search(chunk[-256:]):
            os.kill(pid, signal.SIGTERM)
            return {"early_exit": "needs_input",
                    "tail": output[-2000:].decode("utf-8", "replace")}

    _, status = os.waitpid(pid, 0)
    return {"exit_code": os.WEXITSTATUS(status),
            "raw": bytes(output)}

The PTY path is more expensive and the output is full of terminal control sequences, so the agent should not use it by default. But when it is needed, nothing else works.

3. ANSI and progress-bar normalisation

Whatever you capture, sanitise it before the model sees it. The two transformations that matter are stripping ANSI escape sequences and collapsing carriage-return progress bars into a single representative line.

sanitize.pyoutput normalisation
import re

# CSI sequences (colour, cursor, erase, etc.) plus OSC and a few singletons
ANSI_RE = re.compile(
    r"\x1b\[[0-?]*[ -/]*[@-~]|\x1b\][^\x07]*\x07|\x1b[PX^_].*?\x1b\\")

# A line containing CRs is a progress bar; keep only the last carriage return
# segment, which is the final state of that "line" before it advanced.
def collapse_progress(line: str) -> str:
    if "\r" not in line: return line
    return line.rsplit("\r", 1)[-1]

def sanitise(stream: bytes | str) -> str:
    if isinstance(stream, bytes):
        stream = stream.decode("utf-8", "replace")
    stream = ANSI_RE.sub("", stream)
    return "\n".join(collapse_progress(l) for l in stream.split("\n"))

Without this step, the model's context window fills with noise and its instruction-following degrades visibly. With it, a 12,000-line npm install output collapses to about 60 meaningful lines, which the model can actually reason over.

4. Background execution and event-driven re-entry

For long-running commands, the agent should not block. The right primitive is "start in background, return a handle, notify when something changes." Concretely: a run_in_background tool that returns a process ID, and a notification channel that surfaces output (errors, completion) back into the agent loop as soon as it is meaningful.

This is the architecture Claude Code uses for long-running shells, and the architecture every serious agent eventually arrives at. The reason is asymmetry: most commands are short and can be awaited inline; a few are long and would otherwise destroy the user experience. The system needs to handle both shapes without forcing the model to reason about which is which.

background.pyfire-and-monitor
JOBS: dict[str, asyncio.Task] = {}
EVENTS: asyncio.Queue = asyncio.Queue()

async def run_in_background(cmd: str, *, watchers=()):
    job_id = secrets.token_hex(4)

    async def _run():
        # same streamer as before, but emit events instead of returning
        async for line in stream_lines(cmd):
            for w in watchers:
                if w(line):
                    await EVENTS.put({"job": job_id, "kind": w.kind,
                                      "line": line})
        await EVENTS.put({"job": job_id, "kind": "done"})

    JOBS[job_id] = asyncio.create_task(_run())
    return {"job_id": job_id, "status": "started"}

async def monitor(job_id: str, until: callable, timeout=300):
    deadline = time.monotonic() + timeout
    while time.monotonic() < deadline:
        ev = await asyncio.wait_for(EVENTS.get(),
                                    timeout=deadline - time.monotonic())
        if ev["job"] != job_id: continue
        if until(ev): return ev
    return {"timeout": True}

The agent's prompt is told two things: (a) a job is running in the background, here is its handle, and (b) you will be notified when it produces a noteworthy event (completion, an error pattern match, a stall). The model can carry on with other work in the meantime. This is the single largest UX win in modern coding agents and the single most underestimated piece of system design.

5. Output-conditional re-prompting

Now the reactive piece proper. After every command finishes, the runner inspects the output for patterns that warrant model attention. The patterns are deliberately conservative; the agent should not be re-prompted for noise, only for things that actually change what it should do next.

react.pyoutput-driven dispatch
PATTERNS = [
    ("module_not_found", re.compile(
        r"(ModuleNotFoundError: No module named '(?P<m>[\w.]+)'"
        r"|Cannot find module '(?P<n>[\w@/-]+)'"
        r"|error\[E0432\]: unresolved import `(?P<r>[\w:]+)`)")),
    ("permission_denied", re.compile(
        r"(Permission denied|EACCES|EPERM)")),
    ("auth_required", re.compile(
        r"(Authentication required|Please authenticate|"
        r"401 Unauthorized|fatal: could not read Username)")),
    ("port_in_use", re.compile(
        r"(EADDRINUSE|address already in use|bind: address already in use)")),
    ("compiler_error", re.compile(
        r"(error: |error\[E\d+\]:|TS\d{4}: |SyntaxError: )")),
    ("test_failure", re.compile(
        r"(FAILED|failures?:|✗|×|AssertionError)", re.I)),
    ("oom", re.compile(
        r"(out of memory|killed|OOMKilled|MemoryError)", re.I)),
    ("rate_limited", re.compile(
        r"(429|rate limit|too many requests)", re.I)),
]

def classify(text: str) -> list[str]:
    return [name for name, pat in PATTERNS if pat.search(text)]

REACTIONS = {
    "module_not_found": "Install the missing dependency, then retry.",
    "permission_denied": ("Stop. The command needs elevated permissions or "
                          "a path the user owns. Surface this to the user "
                          "rather than retrying."),
    "auth_required": ("Stop. Ask the user for the credential or how to "
                      "authenticate. Do not store secrets."),
    "port_in_use": ("Find and stop the process holding the port, "
                    "or pick a different port."),
    "compiler_error": ("Read the file at the reported location, fix the "
                       "specific error, recompile."),
    "test_failure": ("Read the failing test and the code under test. "
                     "Determine whether the test or the code is wrong."),
    "oom": "Stop. Investigate memory usage rather than blindly retrying.",
    "rate_limited": "Back off with jitter. Do not retry inside this turn.",
}

def annotate_for_model(result: dict) -> dict:
    text = "\n".join(result["head"] + ["..."] + result["tail"])
    detected = classify(text)
    return result | {
        "detected_conditions": detected,
        "suggested_reactions": [REACTIONS[d] for d in detected],
    }

The detection is heuristic and it is meant to be. The point is not to handle the conditions in code; it is to surface them clearly so the model's next turn is grounded in what actually happened rather than in whatever the model would have inferred from a sea of log lines. A model that sees "detected_conditions": ["permission_denied"] at the top of its tool result is dramatically less likely to retry the command in a loop than one that has to extract that conclusion from line 4,200 of a stack trace.

The pattern, stated baldly: the runner is a controller. It takes raw output, applies a sanitiser, applies a classifier, and produces a structured result the model can act on. The model is not asked to be the controller; it is asked to make decisions inside one.

Self-Healing Loops

The five pieces above are the skeleton. The thing the agent does on top of them is the part that actually feels intelligent. Three loops show up over and over.

The compile-error loop

Every coding agent has some version of this. Run the build. If it fails, read the source file at the reported error location, propose a minimal fix, write it, run the build again. The interesting engineering is in stopping conditions: how many iterations are too many, when does the agent escalate to the user, how does it avoid the failure mode where every iteration trades one error for two new ones.

The trick is to track error fingerprints across iterations. If iteration N produces an error whose fingerprint matches iteration N-1's error, the loop is not converging and should escalate. If the fingerprint set strictly shrinks each iteration, the agent is making progress and can continue. If new fingerprints appear, the agent should be cautious because its last edit introduced regressions.

compile_loop.pyconvergence-aware retry
def fingerprint(line: str) -> str:
    # collapse line/column numbers and quoted spans
    s = re.sub(r":\d+(:\d+)?", ":N", line)
    s = re.sub(r"'[^']{1,80}'", "'X'", s)
    return s.strip()

def converging(prev: set, curr: set) -> bool:
    return curr < prev and len(curr) < len(prev)

prev_fp = set()
for attempt in range(MAX_ATTEMPTS):
    out = await stream_bash(BUILD_CMD)
    if out["exit_code"] == 0: break
    curr_fp = {fingerprint(l) for l in out["tail"] if "error" in l.lower()}
    if attempt > 0 and not converging(prev_fp, curr_fp):
        await escalate("Build is not converging; surfacing to user.",
                       errors=curr_fp)
        break
    prev_fp = curr_fp
    await model_propose_and_apply_fix(out)

The test-failure loop

Same shape, more failure modes. The first decision the agent must make is: is the test wrong, or is the code wrong? Most agents default to "the code is wrong" and start editing application code in response to a test that was never going to pass anyway. The mitigation is a small triage step: read the test, read the code under test, ask the model explicitly which side has the bug before making any edits. Without this triage, the loop produces beautiful, plausible code changes that reliably make the symptoms go away by removing the assertions instead of fixing the bug.

The dependency loop

A command fails with ModuleNotFoundError or Cannot find module or error[E0432]: unresolved import. The reaction policy installs the missing dependency and retries. This is the most retryable class of failure, and the agent should handle it without bothering the user, with two safeties: never install across major-version boundaries without confirmation, and never install a name that does not match the import path closely enough (this is a known prompt-injection vector and a real source of supply-chain bugs).

The cleanest way to show the architecture working is a small replay of a real session. The user asks the agent to run the test suite. The thing this trace illustrates is the division of labour. The streaming runner does the I/O. The classifier flags the conditions. The reaction policy decides which conditions are auto-handleable (module not found, install and retry) and which need the model's judgement (test failure, triage before editing). The model is left to do the small number of decisions that require actual reasoning, not the large number that can be answered structurally.

Failure Modes I Still See

No write-up is honest unless it lists what still goes wrong. These are the recurring problems even with the architecture above in place.

Stalls without output. A command that simply hangs (a deadlocked test, a network call that never times out, a server waiting on a connection) produces no output and therefore triggers no watcher. The mitigation is a stall detector that fires when no bytes have arrived for some duration, but tuning that threshold is annoying: too tight and you kill long-running compiles; too loose and the agent waits five minutes before noticing nothing is happening. Per-command thresholds based on a learned distribution of past runtimes work better than a global default.

Output that confuses sanitisation. A small but real fraction of CLIs emit output that looks like ANSI escapes but is not (e.g., literal text containing \x1b), or that uses ANSI in ways the regex above does not cover (the OSC 8 hyperlink sequences are recent and easy to miss). The fix is to maintain the regex against a corpus of weird real-world tool outputs and treat the sanitiser as living code, not a constant.

Interactive prompts that arrive after a delay. sudo may not prompt for a password if you authenticated recently. A web framework's dev server may print its banner immediately and then wait for the next change before printing anything. The "did this command want input?" detector has to combine textual prompt-pattern matching with a "no output for N seconds after the prompt" timer, and even that is fragile.

Background-job amnesia. The model forgets that it has a background job running and never goes back to check. The fix is on the system side: surface a periodic reminder of active jobs at the top of every prompt, and force the model to acknowledge them before issuing new commands. Otherwise the agent ends up with a graveyard of orphaned servers and leaked file handles.

Pattern matches that change the model's behaviour in unhelpful ways. A retrieval system that classifies everything ends up with reactions firing on noise. The classifier should err on the side of false negatives, and the patterns should be specific enough that they almost never match incidentally. A spurious "auth_required" classification on a stack trace mention of "401" can derail a session.

What to Build, in What Order

If you are building this from scratch, the order I recommend is:

  1. Streaming line-buffered execution with head + tail truncation. Do not start with the rest until this is solid; almost every other failure mode is easier to debug when you can see the output as it streams.
  2. The environment-variable incantation (TERM=dumb, NO_COLOR=1, CI=1, PAGER=cat, DEBIAN_FRONTEND=noninteractive). Set these at the runner level so the model never thinks about them.
  3. ANSI and progress-bar sanitisation. Until you have this, you cannot trust any classifier downstream because the input is full of garbage.
  4. The classifier with the small, specific pattern set. Keep it short. Add patterns only when you see a real failure mode in production.
  5. Background execution with event-driven re-entry. This unlocks the long-running command UX. Do not skip it; the difference in user experience is enormous.
  6. PTY fallback for the small number of commands that need it. Last because it is rarely needed and adds complexity.
  7. The convergence-aware compile and test loops, with explicit triage before edits. This is the reasoning piece and it benefits from all of the above being solid.

The pattern that wins is to keep the model's job as small as possible. The runner is a controller; the model is asked to make the few decisions that are genuinely model-shaped. Every time you push a decision into the runner that does not need the model's judgement, the agent gets faster, cheaper, and more reliable. Every time you push a decision into the model that the runner could have made structurally, you get an agent that is impressive in the demo and frustrating in production.

The terminal is a strange sensor. Treat it that way, build the conditioning layer that closes the loop, and the agent stops feeling like a chatbot with a shell and starts feeling like a colleague who is paying attention.
